# Redis 基础性能报告

## 1. 报告结论

本报告记录阶段 9 在开发机临时 Redis 6 容器上的基础回退基线。四条生产代码路径均完成
正确性断言并取得顺序调用吞吐、P95 和 P99；测试过程未发现数量级异常。

这些数据不包含生产网络、TLS、ACL、连接池竞争、跨可用区、真实 MySQL、RocketMQ 或
多实例业务线程，**不能作为生产容量、SLA 或扩容依据**。

## 2. 测试环境

| 项目 | 配置 |
| --- | --- |
| 日期 | 2026-07-30 |
| JDK | Temurin JDK 17 |
| Redis | `redis:6` 临时 Docker 容器 |
| Cluster | 6 节点，3 主 3 从，测试结束自动删除 |
| 客户端 | Spring Data Redis + Lettuce |
| 调用方式 | 单 JVM、顺序调用；全局 ID 另有 20 线程唯一性测试 |
| 数据隔离 | 随机 `acquiring:it-*` 前缀或精确测试 Key |

执行入口：

```bash
./scripts/run-redis-stage9-tests.sh
./scripts/run-risk-redis-cluster-tests.sh
```

## 3. 测量方法

1. 每个操作在 JVM 内使用 `System.nanoTime()` 记录端到端耗时。
2. P95/P99 使用最近秩百分位；吞吐使用测量样本数除以总测量耗时。
3. 滑动窗口和 MQ 去重先执行 100 次预热，预热样本不进入统计。
4. 锁样本包含 `SET NX` 获取和 token compare-delete Lua 释放。
5. 全局 ID 样本包含 Redis `TIME`、状态 Lua、22 位编号构造与校验。
6. 所有测试同时断言计数、容量、唯一性或 Key 最终状态，避免只测速度不测正确性。

## 4. 基础结果

| 路径 | 测量样本 | 吞吐 | P95 | P99 | 正确性 |
| --- | ---: | ---: | ---: | ---: | --- |
| Cluster ZSet 滑动窗口 | 2000 | 4174 ops/s | 426 µs | 566 µs | 最终 2100 个唯一 member，计数一致 |
| MQ 双桶去重 Lua | 2000 | 1671 ops/s | 1345 µs | 1773 µs | 所有新摘要为 `ACQUIRED` |
| 锁获取与安全释放 | 2000 | 1726 ops/s | 1297 µs | 1817 µs | 每轮释放后 Key 不残留 |
| 全局 ID 顺序发号 | 10000 | 2063 ops/s | 1169 µs | 1684 µs | 10000 个编号全部唯一且格式有效 |

全局 ID 另执行 20 线程、每线程 5000 次，共 100000 个编号，未发现重复。该并发测试用于
唯一性验证，未使用协调遗漏校正或固定速率负载模型，因此不与上表延迟数据混用。

## 5. 容量边界

| 对象 | 测试边界 | 结果 |
| --- | --- | --- |
| MQ 去重桶 | 测试上限 2，写入第三个不同摘要 | 返回 `FALLBACK`；已有摘要仍判定 `DUPLICATE` |
| 频率 ZSet | 测试上限 2，写入第三个交易摘要 | 返回 `ERROR/REVIEW`；ZSet 保持 2 个成员 |
| 全局 ID | 未来毫秒状态且序列达到上限 | 超出重试预算后明确失败，不生成重复编号 |
| 锁租约 | 1 秒 TTL，持有者不主动释放 | 竞争者在 3 秒观察窗口内重新获取 |

生产默认边界为 MQ 每桶 100000 个摘要、TTL 最大 30 天；频率 ZSet 默认 2000 个成员。
本轮只验证边界语义，没有使用最大配置灌入百万级数据。

## 6. 阶段 10 本地有界负载

2026-07-31 使用 `run-redis-stage10-drills.sh` 在一次性 `redis:6` 容器执行：

```text
redis-benchmark -q -t set,get -n 100000 -c 50 -P 16 -r 100000
```

| 命令 | 请求数 | 本地结果 |
| --- | ---: | --- |
| SET | 100000 | 2439024.25 requests/s，P50 0.279 ms |
| GET | 100000 | 3225806.50 requests/s，P50 0.207 ms |

该命令使用 50 个并发连接和 16 级 pipeline，请求量小且运行在本地 Docker；结果容易受到
宿主机调度、pipeline 批量确认和测量窗口影响。它只证明脚本能完成有界持续负载并保留
Redis `INFO` 证据，不能与第 4 节生产代码端到端 P95/P99 横向比较，也不能作为吞吐、
容量或 SLA 承诺。

同一隔离容器还验证 `--bigkeys` 能定位 1 MiB 测试 String，`--hotkeys` 能把 LFU counter
为 41 的测试 Key 识别为最热 Key。这是检测链路的功能证据，不是 UAT/生产 Keyspace 的
容量盘点结果。

## 7. 未取得的性能证据

以下项目没有真实数据源或生产拓扑，不能写为通过：

1. Spring Cache hit/miss、数据库 QPS、连接池等待和 64 许可回源舱壁的容量曲线。
2. UAT/生产真实 Keyspace 的热 Key、大 Key、批量同时过期、长时间内存增长、碎片率和
   淘汰率；本地注入结果不能替代。
3. Redis CPU、网络、命令延迟、连接池使用率和多实例竞争。
4. 风控最大周期 shadow、规则发布失效延迟和 Outbox 积压下的业务 P95/P99。
5. 生产等价 Cluster/Sentinel failover、replica lag、跨可用区和真实 TLS/ACL 开销。

生产准入前必须在 UAT 或等价环境使用脱敏数据、目标并发和真实拓扑重新压测，并把容量
阈值、告警阈值和扩容规则纳入发布审批。
