# 交易生命周期、页面整改与整体验收契约

## 文档边界

2026-11-20，第 01—17 项及四批修复范围经过用户逐项和整体确认后，用户明确授权开始实现；随后补充批准两端角色、岗位编码由后端自动生成。本文记录批准的业务契约、实现范围及验收边界。代码和本地回归不等同于服务已经重启、真实渠道验收或历史交易修复。

适用范围为管理端、商户端及其调用的支付核心授权生命周期。公开接口和 SDK 的既有行为也需要在修复前做一致性核对，不能仅因页面改动而收窄已有业务能力。现有 `PAYMENT` 等其他交易类型的规则保持单独管理。

### 交付环境与真实验收

用户于 2026-11-21 明确要求：收单侧功能、表结构和业务记录的交付目标固定为当前双端实际连接的 `payment_acquiring`。独立演练库和内存库只用于回归，不能以其测试通过代替当前业务库、运行进程和真实页面的验收。涉及上游渠道时，还必须核对实际请求目标与渠道部署版本，不能只更新本地代码就宣称端到端功能已经生效。

当前 ScottChannelA 渠道模块由 `service-payment` 的 runtime Maven 依赖 `payment-channel-scott-channel-a` 提供，修复随该服务重启加载。用户所指的渠道模块应以这条实际依赖及运行时类路径核对，不能因名称相近就改动旁边的独立工程。

### 页面与对外 API 的变更边界（用户明确要求）

1. 页面操作调整不影响对外 API 的业务和逻辑。页面按钮显示、弹窗、原因选项、必填及 200 字说明限制属于两端页面及其专用后台入口的需求，不能自动扩展为公开 API 的新增限制。
2. 对外 API 指商户公开接口及 SDK 所依赖的契约；管理端、商户端页面调用的专用后台接口另行区分。前文泛称“后台校验”不能据此解释为必须修改所有公开入口。
3. 页面整改不能顺带改变对外 API 的参数、必填项、金额与币种含义、可执行动作、状态、幂等、响应码或既有兼容行为。
4. 用户已明确确认，第 11 项“普通授权不支持增量”作为独立业务纠错，也适用于对外 API；页面整改不得影响对外 API 的其他业务和逻辑。本条属于用户明确批准的独立业务纠错。
5. 第 12 项退款故障的排查和验收目标已确认。共享适配器修复范围限于退款及退款查询的明确失败响应解释，以及转换异常时脱敏留证；其他支付类型原有字段验证保持不变。
6. 2026-11-21 真实退款出现 `409 / ORDER_NOT_REFUNDABLE`：退款提交已被渠道明确拒绝且无相互矛盾的资金状态证据时，应立即返回失败并按原有状态机释放预占。不得将所有 `409` 一律判失败；幂等冲突、未知冲突、超时、限流和服务端异常继续保留结果未知。退款查询不套用此提交拒绝规则。

## 已确认的业务规则

### 普通授权

1. `AUTHORIZATION` 成功后，支持多次部分请款，或单次全额请款，累计成功请款金额不能超过授权金额。
2. 已部分请款时，后续仍可请款剩余金额；选择全部剩余额度即本次全额请款。额度用尽后隐藏请款入口。本条及重复请求不得重复请款、退款不恢复可请款额度，用户已明确确认。
3. 普通授权撤销只支持全额撤销。必须原授权成功、尚无任何成功请款、原授权未撤销且没有冲突的未决资金动作，才允许全额撤销；不支持部分撤销。
4. 已有任何成功请款后，不再提供原授权撤销入口；退款针对成功请款处理。
5. 撤销成功后结束该授权生命周期，不能再请款。撤销失败不结束原授权生命周期，其他动作继续按有效授权状态判断。
6. 成功的 `CAPTURE` 记录支持多次部分退款或一次退还全部剩余可退金额，累计成功退款不能超过该笔成功请款的实际金额。
7. 已退款金额不恢复原授权可请款额度。
8. 增量授权仅限预授权。普通授权 `AUTHORIZATION` 不支持增量，API 和两端页面均不提供该能力。本条已在支付核心来源校验中实现，并验证渠道调用前拒绝普通授权增量。

### 预授权

1. `PRE_AUTHORIZATION` 成功且尚未成功撤销、尚未成功完成时，支持撤销、增量授权和预授权完成。其中增量授权只允许通过 API 完成，管理端和商户端均不提供发起操作。
2. 成功增量授权增加原预授权累计额度；失败或结果未确认的增量不能计入已成功授权额度。
3. 预授权完成金额必须大于零，且不超过当前累计成功预授权金额。
4. 同一预授权生命周期只允许一次 `PRE_AUTH_COMPLETION` 成功。完成金额可以小于累计预授权金额。
5. 预授权完成成功后，剩余未使用的预授权额度由发卡行自动释放，收单系统无需处理后续释放，也无需用户或接入方再调用单独 API。
6. 不为该差额在收单系统新增释放任务、释放接口、释放流水、释放回调或释放失败恢复流程。收单系统负责正确记录完成结果、关闭预授权后续操作能力，并按实际完成成功金额控制退款。
7. 完成成功后，原预授权记录隐藏撤销和预授权完成入口，API 也不能继续增量或再次完成，即使历史预授权动作仍为 `SUCCESS`，或旧投影中仍存在剩余额度。两端页面始终不提供增量授权入口。
8. 完成成功后，只在成功的 `PRE_AUTH_COMPLETION` 记录上提供退款入口。退款上限为实际完成成功金额，不能使用完成前的累计预授权金额。
9. 撤销成功即该预授权生命周期终结，不再支持增量、完成或退款。撤销失败不关闭原预授权，仍可按原有效状态进行其他动作。
10. 未成功预授权完成时，不提供退款入口；增量授权记录本身不提供退款入口。
11. 预授权完成明确失败后，原预授权仍然有效，可以重新发起完成、撤销，或者通过 API 继续增量授权；完成成功或撤销成功后，才关闭这些操作。该失败动作保留失败终态，新的一次完成与旧请求的幂等重放分别处理。本条用户已明确确认。

### 退款来源及累计金额

1. 本文授权生命周期内，退款入口只显示在成功的 `CAPTURE` 或 `PRE_AUTH_COMPLETION` 记录上。
2. 原 `AUTHORIZATION`、原 `PRE_AUTHORIZATION`、`INCREMENTAL_AUTHORIZATION`、`VOID`、`REFUND` 记录均不作为该入口的退款来源。
3. 每笔退款必须保留明确的成功资金来源，不自动改绑其他请款，不跨多笔请款合并为一个未定义的退款来源。
4. 每笔成功请款或成功完成各自独立计算退款额度，同时满足整个生命周期的累计资金约束。
5. 退款额度始终按对应成功资金来源计算。用户已明确确认：累计退款成功金额与退款预占金额之和等于该来源实际成功金额时，不再允许退款。预占包含待审批及审批通过后尚未取得最终退款结果的金额；符合释放条件后，再按最新额度判断。
6. 第 09-B 项已全部确认：有剩余未预占额度就允许继续申请退款，后台保证累计成功退款金额加全部预占不超过该笔实际成功金额；审批和最终退款结果按下文规则衔接。
7. 可退额度为零时隐藏退款入口；部分退款成功后，如还有可退额度，则保留该来源记录的退款入口。

## 状态关联、并发和幂等约束

以下是修复时需要验证的资金保护约束，不表示本轮已经完成代码审查或运行验收。

1. 原交易动作的历史结果与当前生命周期是否可操作分别表达。原预授权曾成功的事实保持可追溯；后续撤销或完成通过关联事实关闭对应能力，不能依靠改写原成功记录来驱动按钮。
2. 管理端列表、商户端列表、详情、菜单和实际接口使用一致的业务判断。业务条件不成立时隐藏操作，不保留无法点击的业务按钮。
3. 前端隐藏不替代服务端校验。服务端在受理和实际执行时检查最新生命周期状态、金额、来源、权限及幂等身份，拒绝过期页面或直接接口请求。
4. 同一生命周期的请款、撤销、增量和完成必须防止相互冲突的并发推进。结果未知的请求不是明确失败，不能在未查清时放行相反资金操作。
5. 同一预授权并发发起两次完成，最多只能形成一次成功资金动作；重复回调和补查不能重复累计完成金额。发卡行对剩余预授权的自动释放不属于收单系统资金任务。
6. 每笔多次部分请款、部分退款都有独立动作身份；同一动作的超时重试和重复提交沿用相同幂等身份，返回原结果，不能增加累计金额。
7. 多次请款和退款同时校验来源动作额度与生命周期总额度，防止单笔越限和合计越限。
8. 已成功、已明确失败的具体动作保持终态保护。失败后新的一笔合法操作与旧动作重放分别处理，不能将重复请求自动变成新的资金动作。
9. 金额按币种精度及既有冻结汇率分别维护标签口径和渠道交易口径；最后一笔剩余额度处理既有换算尾差，不能重新取实时汇率或用浮点数决定资金边界。

### 第 09-A 项未决动作冲突规则（用户已确认）

1. 同一原授权或原预授权存在处理中、结果未知的请款、预授权完成、撤销或增量请求时，页面隐藏与之冲突的操作，API 同样拒绝新发起的冲突请求。
2. 同一请求的重复提交返回原动作及其当前结果，不创建第二笔资金请求；原动作仍可查询和接收回调。
3. 原动作明确失败后，按照原交易当前有效状态重新计算后续能力；原动作成功后，按照累计金额和生命周期规则重新计算后续能力。
4. 用户明确说明，现有系统勾兑定时任务会自动勾兑并同步对应订单状态。同步完成后，后续操作随最新有效状态自动显示或隐藏，无需人工解锁。复用现有勾兑链路，不新增独立恢复定时任务。
5. 需要在后续验收中检查勾兑后订单状态、列表和详情数据及操作可见性的一致性；具体页面数据刷新机制在实施方案中核对，不在讨论阶段假定已经有推送或轮询实现。

## 第 09-B 项退款额度预占

### 用户已确认的核心上限

1. 以具体成功请款或成功预授权完成记录的实际成功金额作为上限。退款预占金额必须与累计退款成功金额一起计算，不能只扣除成功退款金额。预占包含待审批，以及审批通过后执行中、真实渠道处理中或结果未知的金额；同一退款跨阶段不重复计算。
2. 设该来源实际成功金额为 T，累计退款成功金额为 S，退款预占总额为 P。当 S + P = T 时，不允许新增退款；页面隐藏退款入口，后台同样拒绝新增退款。S + P > T 作为异常越限情况同样禁止新增，不通过本轮直接修复历史数据。
3. 一笔处理中退款转为成功时，相应金额从 P 转入 S，S + P 不变，不能因此恢复可退额度或重复扣减额度。
4. 一笔处理中退款最终明确失败后，释放它在 P 中的占用，再按最新额度重新计算退款能力。不能仅因请求超时或尚未取得最终结果就提前释放。
5. 新退款金额必须满足该来源的剩余额度约束，后台以最新数据作并发保护，不能让多个请求各自读取旧余额后同时超过 T。重复请求、回调或勾兑不能重复预占、累计或释放。
6. 复用现有自动勾兑及回调链路同步结果和额度，页面按最新有效数据重新计算金额与退款入口；不同资金来源的额度不能混用。
7. 例：成功请款 1,000，已成功退款 200，退款处理中 800，此时可退为零，禁止再退款。800 最终成功后，成功退款变为 1,000，仍禁止退款；800 最终失败并释放后，可退恢复为 800。

### 审批与退款结果的预占衔接（用户已确认）

1. 退款进入待审批时就预占相应可退额度，不能等审批通过或调用渠道后才占用。
2. 审批拒绝，或者审批过期且尚未执行时，释放该笔退款预占。
3. 审批通过后继续保持原有预占，不在审批通过时释放，也不为同一退款再占用一次。
4. 最终退款成功时将预占转为成功退款累计；最终明确失败时释放预占。结果未确定期间继续占用，不能将审批过期误用于释放已执行但尚未明确结果的退款。
5. 审批、执行、回调和自动勾兑的重复处理不得重复预占、结转或释放；衔接过程不能产生额度短暂空档导致其他请求超额占用。

### 剩余未预占额度继续受理（用户已确认）

1. 在 S + P < T 时，即使同一来源已有待审批或处理中退款，仍允许对剩余未预占额度继续申请退款。
2. 本次申请金额 R 必须大于零，且 S + P + R 不超过 T。后台根据最新数据原子校验并新增对应预占，防止并发请求同时使用同一份剩余额度。
3. 例：成功请款 1,000，成功退款 200，已有预占 300，还允许申请不超过 500 的新退款；申请 500 后 S + P 达到 1,000，不再允许新增。申请超过 500 必须拒绝，不形成超额预占。

## 退款处理中故障的边界

1. 渠道明确成功才累计成功退款并推进下游资金事实；明确拒绝才形成受控失败终态。
2. 超时、网络中断、空响应、畸形响应、解析异常或无法核实的渠道结果需要保留未决状态，并按原退款身份查询或等待可验证的通知。不能因页面希望立即结束就将未知结果改为成功或失败，也不能重新发起一笔退款。
3. 用户当前接入的几个渠道退款通常直接返回成功或失败。本次异常进入“处理中”按退款故障排查，不将其解释为正常的异步退款流程。重点核对实际退款响应、适配器解析、成功与失败状态映射及异常处理，是否将本可确定的结果误转为未知。
4. 2026-11-20 的退款 `202611201447565519191`：14:47:57 出现 `CHANNEL_RESPONSE_INVALID`、`ChannelResponseException`、`outcomeUncertain=true`；14:48:33 对原退款进行 `QUERY`，返回 `REFUND_NOT_FOUND` 后转为失败。记录的是首次响应解释故障及后续补查，不是重复退款。
5. 该首次异常缺少 HTTP 状态和脱敏响应正文证据，不能据此认定具体根因。需要验证渠道错误响应解释、响应证据保存时机及查询身份；保存证据不得引入 PAN、CVV、密钥、令牌或完整敏感报文泄露。
6. 用户已明确确认：本次补查取得 `REFUND_NOT_FOUND` 后转为失败的当前处理没有问题，保持现有判定，不再列为待修改项。
7. 用户认可待审批、渠道处理中、结果未知、明确失败应清楚表达阶段和原因。真实超时等无法确认资金结果的技术异常仍沿原退款身份处理，不因渠道通常同步返回就强行确定成功或失败，避免重复退款。
8. 本轮不重试或修复该笔历史资金记录；代码故障修复和历史交易处置分别说明范围、证据与授权。

## 业务验收场景

1. 授权 1,000，依次请款 200、300、500，三笔均可成功；任何时点都不能累计超出 1,000，全部请款后原授权隐藏请款和撤销。
2. 授权 1,000，尚无成功请款时只能全额撤销 1,000；部分撤销被拒绝。全额撤销成功后页面和直接接口均不能请款，重复撤销不重复释放。
3. 授权 1,000，已成功请款 200 后，原授权不再出现撤销；仍可对剩余 800 请款，对成功的 200 请款记录退款。
4. 某笔成功请款 300，先退款 100，再退款 200，可全部退完；不能将该笔退款上限误用为整个授权或其他请款的金额。
5. 预授权 1,000，通过 API 增量成功 200，完成上限变为 1,200；两端均不提供增量授权入口，但显示新累计额度。失败增量不增加上限，未决增量不能作为确定额度。
6. 累计预授权 1,200，只完成 1,000 成功；剩余 200 由发卡行自动释放，收单系统不新增释放动作或任务。原预授权不再出现撤销和完成，API 也不能再增量；只能从成功完成记录退款，累计不能超过 1,000。
7. 上一场景即使原预授权历史状态仍为成功，或旧页面仍显示 200 剩余，也不能再完成。并发、重放、回调和补查均不能产生第二次成功完成或重复累计。
8. 预授权撤销失败后，仍可对有效原预授权通过 API 增量或从合规入口完成。预授权完成明确失败后，原预授权仍有效，可重新完成、撤销或通过 API 增量；只有完成成功或撤销成功后才关闭这些能力。明确失败的新尝试与旧请求重放分别验证。
9. 原预授权成功但尚未完成、增量授权成功、失败完成、退款成功等记录均不出现退款入口；成功完成记录有剩余可退额度时出现退款入口。
10. 两笔来源请款分别为 200、300，一笔的退款和待处理预占不能导致其累计超出自身额度，也不能误扣另一笔来源的可退金额。
11. 成功请款 1,000，退款成功 200 加预占 800 时，两端隐藏退款、后台拒绝新增；800 进入待审批即占用，审批通过继续占用，最终成功后仍不可退款，审批拒绝、审批过期且未执行或最终退款明确失败时释放对应占用。若成功退款 200、预占 300，则允许继续申请不超过 500，超过必须拒绝，并发受理同样不得突破上限。重复请求、审批、回调和勾兑不能改变应有合计，已执行退款不能仅因审批过期释放。
12. 当前渠道直接返回退款成功或失败时正确形成对应结果，不因解析和状态映射错误转为未决；HTTP 错误、超时、响应缺字段、未知结果后查询及重复回调分别验证。本次 `REFUND_NOT_FOUND` 转失败规则保持不变，不能通过直接改库制造通过结果。
13. 两端权限、列表、详情、菜单和接口保持一致；用过期页面或直接调用接口不能绕过已经关闭的能力。
14. 多币种、小数精度、冻结汇率和末笔尾差分别验证，退款不得超过实际成功请款或完成金额。
15. 普通授权经 API 请求增量时必须拒绝，不能发出增量渠道请求或改变金额；符合既定生命周期条件的预授权可以经 API 增量，两端始终无增量入口。已纳入支付核心定向回归。
