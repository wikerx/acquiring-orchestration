# 商户支付方式开通与交易能力闭环需求

## 2026-11-19 14:32

文档阶段：**需求评审补齐稿 R1.2（2026-11-20）；记录历史兼容取证及授权到期边界的业务决定，配套[技术核验版方案 V1.3](merchant-payment-capability-design.md)。**

本轮用户已暂停商户支持工单，保留其设计。当前工作是明确商户支付方式的申请、审批、费率、通道配置、可用性和后续监控之间的业务关系。两张其他系统截图仅提供业务参考，不作为本系统菜单、字段、状态或通道配置的既定设计。

本次仅更新需求文档，属于 R0。后续若改变支付受理门禁、审批授权、费率使用或实际渠道选择，将涉及 R2/R3，须在设计阶段另做影响、兼容、迁移与验证分析。本文件不新增 API、SQL、业务枚举或路由算法，不代表研发启动。

## 一、核心目标

让商户能明确回答以下问题，让管理端能完成相应的配置与治理：

1. 平台当前已启用了哪些支付方式，我可以申请其中哪些方式？
2. 我申请了哪些支付方式，每一项审批结果是什么？
3. 平台正式允许我使用哪些支付方式，允许的范围是什么？
4. 每个支付方式对应什么收费规则，何时生效？
5. 已获批的支付方式是否已经具备交易条件，不能使用时原因是什么？
6. 平台是否已配置符合条件的通道；是固定通道，还是需要从多个候选中选择？
7. 后续如何在商户整体和具体支付方式层面查看成功率、失败原因、风控、欺诈、拒付及适用的卡组织监控指标？

目标闭环：**从平台已启用目录提出申请 → 逐项审批 → 形成商户授权范围 → 关联生效费率与有效 MID → 在已批准范围内自动匹配渠道/MID 能力 → 固定通道或有效多候选选择关系 → 自动检查就绪 → 交易执行按真实条件校验 → 结果按原支付方式与实际执行信息归集 → 监控反馈及受控调整。**

费用配置、审批和 MID 绑定可以按现有业务流程先后完成；上面的箭头表达事实关联，不要求为了满足先后顺序重新绑定已有有效 MID。系统需要在各条件变化后重新判断，不额外增加一次逐项人工启用。

| C30 | 历史商户某方式没有成功交易时，有可核实的记录证明在基线时点确实具备收款条件，允许按商户及方式逐项登记并复核后纳入冻结的历史兼容清单 | 用户在历史兼容核验中明确确认 |

## 三、现有能力与缺口

本节来自本轮只读源代码核对，不等于运行环境验收或全系统完整审计。

| 已存在的基础 | 本轮看到的能力 | 不能据此推断的内容 |
|---|---|---|
| 商户当前费率 | `MerchantFeeController`、`MerchantFinanceServiceImpl`、商户 `finance/fee` 页面展示生效费用版本、适用支付范围、收费触发点、标准/阶梯等规则 | 费用规则中覆盖某支付方式，不证明商户获准开通它 |
| 商户渠道/MID 绑定 | `MerchantChannelMidBindingDO`、双端相关查询与管理功能 | 一个绑定不能代替逐项商户申请和批准事实 |
| 能力就绪检查 | `MerchantPaymentCapabilityReadinessService` 按交易动作、支付方式/卡品牌、币种展开交集，检查候选冲突和生效费用覆盖 | 配置可路由摘要不能充当商户逐项申请结果；后台静态检查不保证每次真实付款成功 |
| 支付运行时通道选择 | `DefaultPaymentChannelRouteService` 对候选进行筛选；单候选直接使用，多候选存在原币优先/优先级等既有选择规则，无法唯一选择时拒绝 | 管理页面有路由配置不代表所有配置已被当前运行时消费；设计时须核实真实调用链 |
| 商户准入、接入配置及费用审批基础 | 已有商户准入、来源网址/IP 审批、费用审批等不同业务 | 这些审批不能直接解释成“每个商户支付方式均已申请并批准” |

本次需要建立的核心业务事实是：**商户获准使用的支付方式范围**，并将它与既有费率和执行能力衔接。不得另建一套互相矛盾的费率或通道事实。

## 四、统一业务概念

| 概念 | 业务含义 | 不应混淆的内容 |
|---|---|---|
| 支付方式目录 | 平台统一登记的业务支付方式，带统一名称、Logo、分类及启用状态；商户当前申请目录只展示平台已启用项 | 后台登记不等于启用；平台已启用也不等于该商户已获批或已配置就绪 |
| 支付类型 | 卡支付、钱包等展示分类；沿用现有字典含义 | 不将卡品牌、交易动作、渠道名称混为一列 |
| 具体支付方式/卡品牌 | 商户能识别和逐项申请的 Visa、Mastercard、Apple Pay 等业务项 | 不擅自将 Visa 写成现有 `paymentMethod` 协议的新枚举；底层映射在设计时确认 |
| 申请与审批 | 一次请求和每一项的申请范围、审批意见、来源及历史 | 申请拒绝不应抹掉商户原先已生效的其他授权 |
| 商户授权范围 | 平台正式允许该商户使用的支付方式及有效限制 | 独立于费用配置和渠道绑定 |
| 对应费率 | 当前生效且适用于该支付方式、交易动作等条件的规则 | 不把草稿、模板报价、未来版本当作当前收费 |
| 配置就绪 | 费率、通道绑定、执行能力等必要条件已满足 | 不保证每笔请求都能通过风控、限额或渠道处理 |
| 当前可交易 | 对明确环境和交易条件，当前允许发起相应交易 | 不是保证付款成功，也不应只是一个长期不变的绿色标签 |
| 渠道/MID 候选 | 对某项具体交易条件，符合约束的真实执行目标 | 数量按有效候选去重，不按配置行数或渠道总数粗算 |

Apple Pay 等钱包的用户选择入口和实际承载的卡组织/资金来源分别保留。按 C22，钱包仅检查钱包自身的商户授权；底层卡品牌由渠道/MID 限制，不再次要求商户直接卡支付授权。钱包不会带出直接 Visa 等权限，Visa 获批也不会自动开通 Apple Pay。底层品牌未知不等于钱包未获准，能否执行由真实渠道协议和能力决定。

## 五、商户端业务需求

### 5.1 支付方式全景

商户当前申请目录展示平台已启用的全部支付方式，包括卡品牌、钱包及其他已启用类型，不仅展示卡支付。平台未启用的项不出现在当前申请目录，本期不设置未接入方式的开通意向流程。每种方式是否可申请还取决于该商户的既有授权、活动申请等情况。

平台停用方式后，不再列为当前可申请/可交易项；已有申请、授权变更、收费和交易历史仍按权限保留，以解释历史事实，不能删除或改写成“从未开通过”。历史查询不等于将停用项继续放入当前申请目录。

商户能在同一业务入口查询自己支付方式的完整情况，至少包含：

- 统一 Logo、名称、支付类型。
- 是否可申请、是否已有活动申请、逐项审批进度和意见。
- 是否已获准开通；如暂停、终止或到期，展示相应说明。
- 当前配置/使用情况：已具备条件、待费用配置、待通道配置、条件受限、暂不可用等可解释结果。
- 支持的交易币种、交易动作和其他经过确认的适用范围；方式获批后，各动作继续由既有业务权限、渠道/MID 和原状态机约束，不能显示为全部动作无条件可用。
- 当前生效费率摘要、完整规则入口、生效时间与版本；必要时展示待生效版本，但明确区分。
- 对应可进行的动作，例如申请、补充资料、查看结果、查看费率；不能给出无权限或无实际能力的假按钮。

具体菜单位置、列表/卡片、页面数量和布局留待设计。本阶段不预先增加多个相互独立、不能跳转的页面。

### 5.2 商户申请

1. 商户可以一次选择多个支付方式；逐项记录申请内容，系统显示本次实际选择数量。
2. 已有待审项不重复提交；已开通项如需扩大范围，走变更申请，不覆盖既有批准范围。
3. 对退回项补充后重新提交；对拒绝项按规则重新申请，保留历史理由。
4. 商户可以追踪每项结果；同一申请部分完成时，不把全部标成通过或全部失败。
5. 撤回申请只影响尚未批准的申请项，不顺带关闭已经允许使用的方式。
6. 商户申请身份和数据范围来自可信登录身份，不允许请求中任意指定其他商户。
7. 本期申请表只选择具体支付方式，不要求选择交易币种、消费者地区、账单国家或发卡国家；币种/地区等限制沿用后台实际能力和配置，商户可以查看适用限制，未填写不表示无限制。
8. 后台币种/地区能力变更沿用其配置治理；不另建一套与后台可能冲突的商户申请范围。

### 5.3 与当前费率衔接

1. 从支付方式能查看适用费率，从当前费率能知道覆盖哪些支付方式及这些方式的开通情况。
2. 同一费率覆盖多种方式时复用同一生效规则，不复制出多套可能漂移的金额。
3. 规则中 `ALL` 或集合范围只表达收费适用范围，不能自动授予未批准的支付方式。
4. 支持标准/阶梯、比例/固定、上下限、收费触发点，以及按交易动作区分的费用；不能压成一个看似完整的“百分比”。
5. 风控服务费、争议费、结算换汇等非单一方式独占费用，应按真实规则说明适用性，不能硬拆成每种方式一份固定费率。
6. 未获准的支付方式即使已有配置费率，也须说明“费率已配置，支付方式未开通”；没有对应费率时不能显示 0 费率。
7. 商户只看获准公开的商户收费，不展示平台渠道成本、内部议价、模板来源或秘密凭据。

## 六、管理端配套需求

### 6.1 代申请与逐项审批

1. 平台人员选定单一商户后代申请，明确记录来源、申请人、原因与各支付方式。
2. 商户发起与平台代申请进入一致的审批规则和记录体系；不能通过代申请绕过审批。
3. 申请人不能审批自己的申请；审批人同时需要动作权限和该商户数据范围。
4. 审批人逐项查看申请、现有授权范围、费用情况和相关渠道能力摘要，给出通过、退回补充或拒绝意见。
5. 审批通过形成正式授权；只批准范围内的方式。不得因某渠道支持额外方式，就自动替商户开通。
6. 审批意见、修改、重复提交、并发审批与后续撤销均可追溯；不覆盖旧批准记录。
7. v1.4 提到的高权限开通仍受另一人复核约束，复核通过前不能直接形成有效授权；具体操作名称在设计时确定，不能给用户“点击后立即开通”的错误预期。

### 6.2 从批准到可用的配置跟进

平台人员需要对每个获批支付方式看到：

- 商户允许范围和本次批准结果。
- 当前费用覆盖、缺失、冲突、未来生效情况。
- 可匹配的渠道及 MID，各自支持与不支持哪些申请条件；不把整条渠道粗略标为全部支持。
- 已绑定与未绑定情况，固定通道或多候选选择关系。
- 尚未就绪的全部原因、责任配置入口和配置后复查结果。

审批通过后可以继续完善配置；不要求为了通过申请先伪造出可交易状态。配置步骤的执行者和是否追加配置审批，在设计前结合既有权限与审批规范确认，不能从本次开通审批自动取得任意配置权限。

**自动关联与就绪的已确认规则：**

1. 商户批准范围是授权上限；平台启用目录、渠道能力、MID 能力/限制、商户有效绑定及费用共同约束实际可用范围。
2. 当已获批方式具有支持它的有效渠道/MID 绑定，适用费率生效且固定/多候选选择条件满足时，系统自动判定该方式在对应条件下就绪，不再增加一层“给该 MID 逐项启用支付方式”的人工操作。
3. 已先绑定 MID 后批准方式，或者先批准后绑定 MID，最终条件相同则结果相同；不要求解绑重绑来触发能力获得。
4. 同一 MID 支持 Visa 和 Mastercard，商户仅获批 Visa，只自动关联 Visa。Mastercard 既不因绑定自动获批，也不进入商户可支付范围。
5. 有效费率仍是已确认的交易条件；MID 已绑定但缺少适用费率，须显示待费用配置，而不是直接可交易。
6. 多个有效候选还须满足明确且运行时有效的选择规则；不因自动关联而随机挑选或绕过冲突。
7. 平台启用、审批、费用、渠道/MID、绑定和策略变化后自动重新判断；仍保留每项授权与配置事实，不能以自动计算抹掉审批历史。

### 6.3 支付方式生命周期

本期完整覆盖新增授权、支付方式集合扩大/缩小、暂停新业务、恢复、终止和到期。单项币种/地区限制继续由原后台配置治理，不增加新的申请范围。

- 首次开通及终止后重新申请：按原双人规则提审，复核前无新授权。
- 暂停、恢复、终止、有效期调整：有相应权限的管理人员可以单人处理，原因、商户范围及版本校验必填，记录真实前后事实。
- 终止不能直接恢复；新的开通申请通过后保留同一商户/方式身份与过去历史。
- 授权到期按有效时间判断，定时任务用于刷新展示、通知与跟进；定时任务延迟不能使新交易继续放行。
- 到期后的重新生效通过有效期调整处理，仍受现有授权状态限制；仅调整有效期不能恢复暂停状态或使已终止项复活。具体边界在方案状态矩阵中统一表达。

任何暂停或限制必须有原因和审计。变更应清晰影响新业务，不能无条件让原交易查询、回调、退款、请款等后续动作全部失效；历史动作继续由所属业务权限、原交易状态与原始执行信息判断。

商户、支付方式、费率、通道、MID、策略任一配置变化，都可能改变就绪情况，双端应能反映变化，不能永久沿用审批当时的一次性检查结果。

### 6.4 配置跟进与时间变化

审批事项终结与配置跟进分开处理。获批后不满足约定业务条件时，在现有统一运营待办产生待分派事项；认领、分派、转派沿用原权限。费用与 MID 等多个缺项作为同一方式、同一跟进条件范围内的原因集合维护，不拆成重复孤立工单。人工标记完成不能制造配置就绪，最终仍由真实条件重算。

条件配齐后自动结束相应跟进；其后因到期或停用再次失去条件时，按真实新一轮状态重新打开跟进，保留处理历史。暂停、终止等主动授权限制与配置故障分开，不因故意暂停而反复创建无意义配置待办。

自然生效、到期同样触发重算。正常运行时，后台跟进同步与通知处理的时限为 1 分钟；页面主动查询重算，新交易最终检查不等待此时限。通知处理与邮件最终收件分别留痕，异常可追踪、告警和补偿。

## 七、审批、费率、配置与交易状态的关系

至少区分四个独立事实，不用一个“启用”覆盖所有含义：

1. **审批结果**：本次申请项是否通过。
2. **授权情况**：商户当前是否正式获准使用该方式。
3. **配置就绪情况**：对应费率、执行候选与必要能力是否配齐。
4. **交易可用情况**：在明确的请求条件下是否允许受理。

| 示例情况 | 商户应理解的结果 | 能否仅据此发起新收款 |
|---|---|---|
| 有 Visa 费率，但未申请/未获批 | 已有收费配置，尚未获准使用 Visa | 不能 |
| Visa 审批通过，尚无费率或通道 | 已获批，待配置，并给出缺项 | 不能 |
| Visa 费率与通道齐备，但授权被暂停 | 已开通过，目前暂停，并说明原因 | 不能 |
| Visa 获批、费率有效、单一候选满足条件 | 配置就绪，可在允许范围内收款 | 仍逐笔校验身份、风控、限额等条件 |
| Visa 获批，但仅部分币种具备候选 | 仅指定币种/动作可用，其他条件受限 | 只允许符合条件的请求 |
| Apple Pay 已获批且平台已启用，但当前未绑定支持它的有效 MID | 已获批，待通道/MID 配置 | 不能 |
| MID 支持 Visa、Mastercard，但商户只获批 Visa，且费用等条件满足 | 自动具备 Visa；Mastercard 仍未开通 | 仅允许批准并满足条件的 Visa 请求 |

上表用于解释业务事实，不是最终状态枚举设计。平台未启用的方式不进入本期当前申请目录；平台已启用的某方式仍可能因为该商户尚无支持它的有效 MID 而待配置。

实际受理至少受到商户状态、正式授权范围、请求环境和条件、适用费用、有效执行配置、平台能力及风险限制的共同约束。仅在页面隐藏方式不足以阻止越权请求；OpenAPI、收银台和 PayByLink 等相关入口必须采用一致的受理事实。

“可用”需要声明评估范围和时间；后台临时故障和资金/风险控制变化可能影响单笔请求，不能把配置就绪描述为必定付款成功。

### 7.1 收银台真实方式与前端付款组件

依据 v1.4 评审后的用户澄清，收银台展示的始终是商户真实获准且满足基础条件的支付方式。前端尚未接入 Apple Pay、Google Pay 等真实按钮加载，是付款交互的适配问题，不得因此将商户的已授权事实改为未开通，也不得把平台尚未启用或商户尚未获批的方式当作占位项加入。

| 业务与交互情况 | 商户后台 | 收银台付款选项与提交 |
|---|---|---|
| 平台未启用或商户未获批 | 按目录/权限规则显示真实事实 | 不加入该方式 |
| 已获批，但缺有效费率、有效 MID 或存在选择冲突 | 保留已授权，显示缺项与配置入口 | 不加入该方式 |
| 授权、费用、有效候选及订单限制等基础条件满足，但对应钱包按钮加载/交互尚未接好 | 显示真实授权及能力，付款交互状态单独说明 | 展示真实 Logo/名称及相应交互预留；未就绪时不可付款，不把其误标为商户未开通 |
| 业务条件满足且前端组件和后端执行均已就绪 | 展示真实能力 | 加载真实组件，按既有流程提交并再次校验 |

要求：

1. 展示名单由后端真实业务事实与当前订单/链接/会话限制共同决定，不能从前端组件是否存在反推商户开通范围，也不能用前端写死名单替代授权。
2. 前端完成适配的方式加载真实组件；尚未适配的方式预留合适的说明和交互容器。未生成真实二维码时不提供可扫码的假码，按钮未就绪时不渲染貌似可操作的假支付按钮。
3. 建设中未适配与已适配组件的临时加载失败须可区分，均不能无限加载。消费者看到清楚、可操作的提示，例如“此支付方式暂不可付款，请选择其他方式”；不暴露内部实现细节。
4. 前端组件未就绪不能触发未实现的付款动作；即使前端按钮存在，后端仍须依据真实执行能力及权限校验。不能仅凭前端未接好就断言后端未实现，也不能仅凭已授权就假定前后端均已完成。
5. 展示预留项不等于可提交，不计为真实交易成功或失败，也不作为商户已具备完整付款体验的证明。

## 八、固定通道与多候选选择需求

1. 判断单位是同一商户、同一具体支付方式/卡品牌、同一交易动作、币种及其他实际约束下的有效执行候选。
2. 零候选：待配置或当前无可用执行目标；不得假装存在默认通道。
3. 一个有效候选：固定使用该目标；前台无需要求商户理解或配置复杂路由。
4. 多个有效候选：需要有明确、可解释且当前执行链实际采用的选择规则。
5. 同一渠道两个 MID 也可能是两个候选；两个渠道如果分别只支持不同币种，则未必在某笔交易上构成多候选。
6. 去重重复绑定/重复能力记录；不能因配置记录重复而虚增候选数量。
7. 全部候选不满足条件或选择存在冲突时，必须给出明确原因，不随机挑选。
8. 单一目标也要检查有效期、停用、币种、动作、卡品牌、地区等已适用约束；“固定通道”不免除基础校验。
9. 本次需求包含开通能力与通道/候选的关联闭环；新的动态成功率路由、权重、自动故障切换、成本择优等是否实施另行定范围，不自动重启全部路由重构专项。
10. 原交易退款/请款/查询等是否固定原通道，遵守现有业务契约；新增方式配置不能把历史后续动作改投当前新通道。

## 九、后续监控要求与本期数据基础

### 9.1 用户明确要求的监控方向

双端后续需要支持商户整体与支付方式层面的交易成功率、失败原因、风控分析、欺诈/拒付率及适用卡组织监控；管理端还需要按权限进一步查看渠道、MID 等内部执行维度。

本期把可关联、可解释、可追溯的数据口径列为必需基础；具体监控页面、告警策略和分期安排在需求确认后单独设计。不是本期只做审批页面，等以后再猜交易属于哪个支付方式。

### 9.2 必须能区分的统计对象

- 商户业务订单、付款尝试、真实系统订单、实际渠道尝试，以及回调事件，不能混为同一笔数。
- 端到端付款成功率、实际到达渠道后的成功率、支付方式占比，需分别定义分子分母和时间口径。
- 失败原因区分商户未获准、配置未就绪、风控拒绝、渠道失败、用户操作和未知/处理中等；处理中或未知不能直接当作明确失败。
- 支付入口/具体方式与底层卡品牌分开归集；如 Apple Pay 承载 Visa，既能分析 Apple Pay，也能归入适用的 Visa 维度，汇总时不能重复计数。
- 配置地区、账单国家、发卡国家、IP 地区和清算区域不可互相代替；采用哪一类需在该指标或准入规则中明确。
- 退款、拒付、欺诈通知等延迟事件关联原交易；后续事件补齐和去重不能改变历史交易身份。
- 区分测试/生产、币种、交易动作和统计周期；币种金额不能直接相加。
- 无数据、不适用、数据缺失与真实为零分别显示，不补造支付方式、审批、成功或风控事实。

每笔历史业务应能追溯当时适用的授权范围、收费版本与实际执行目标；不能根据现在的费率或绑定修改历史归属。

对已通过必要身份和请求校验、确实进入付款受理的尝试，记录入口、商户、规范支付方式、原交易动作、稳定尝试/幂等身份、失败阶段、结果、发生时间以及可空的真实系统订单关联。收银台优先复用现有尝试与事件，OpenAPI 优先复用交互事实；重放同一业务请求不新增独立尝试。纯页面选择、组件未就绪、无效认证请求与付款失败分别统计，不拿技术请求日志行数直接作付款分母。

### 9.3 VAMP 的适用边界

Visa 官方说明将 VAMP 定位为收单机构与商户的欺诈、争议及枚举攻击监控计划；因此不能把它当作覆盖所有支付方式的统一“拒付率”。参见 [Visa 官方 VAMP 说明](https://corporate.visa.com/en/sites/visa-perspectives/security-trust/introducing-visa-acquirer-monitoring-program.html)。

后续需求必须区分官方适用口径、内部估算与业务分析切片：

1. Visa 适用交易的官方/受认可数据范围和聚合对象，不能随意换成某钱包的全部交易量作为分母。
2. 按支付方式/钱包切片可以用于内部定位贡献，但不能冒充卡组织正式判定结果。
3. 卡组织阈值、区域、生效版本及数据到达延迟需独立确认；本文不固定任何阈值或实施公式。
4. 尚无必要欺诈、争议或卡组织数据时显示缺失/估算，不能仅凭支付失败记录生成“真实 VAMP 指标”。

## 十、权限、通知与变更可靠性

### P0：不可绕过的业务约束

- 商户只能申请和查看本商户授权与公开费率；管理操作同时检查角色权限、商户范围和申请人与审批人分离。
- 未获准、超范围或暂停的方式不能仅因有费率、MID 或页面参数就发起新业务。
- MID 自动关联只能收敛在商户已批准范围内，不能把 MID 的全部能力自动转为商户授权；平台启用状态同样不代替商户审批。
- 后端审批、配置就绪和实际交易受理口径一致；异步刷新、缓存过期不能成为永久越权窗口。
- 同一申请项重复提交/审批不能重复授权；旧页面审批不得覆盖新版本范围。
- 审批通过、配置完成和真正可用分别记录，不因消息发送失败抹掉成功审批，也不因消息送达标记可用。
- 审批记录、授权变更、费率、配置和实际执行信息可追溯；不暴露渠道凭据、完整卡数据或内部成本。

### P1：完整业务交付

- 支付方式目录和商户支付方式全景；本商户的申请、逐项结果、授权及使用限制。
- 双来源申请、逐项审批、退回补充、拒绝与受控变更。
- 费率贯通、固定/多候选关联、就绪缺项定位和真实受理约束。
- 关键进展通知、查询、审计、双端权限、多语言与真实分页。
- 未来监控所需维度和当前事实的完整性检查。
- 数据模型先核对既有表的归属、基数、生命周期、索引与兼容性，优先复用字典、费用、MID、商户审核、统一待办和可靠失效等设施；不得仅按页面或功能入口拆出平行数据体系。设计中的新增数量仍须通过评审。

后续监控图表属于用户明确的后续目标，不因分期而变成可随意取消的可选功能。深度算法和展示方式属于后续设计内容。

### 通知需求

商户至少收到提交回执、逐项审批结果、退回补充、已具备使用条件、重要暂停/恢复/终止以及适用费用变化的通知。管理端需要待审和配置待跟进事项，避免批准后无人继续配置。

通知只传达已经提交的事实，附件/邮件不能泄露内部通道参数。准入变更与可靠通知意图必须同事务保存，提交前不发送；提交后进程中断也须可恢复，优先复用 sys_mq_outbox 与既有邮件记录/模板，不另建本功能通知表。

相同业务变更的通知身份稳定，重试不重复创建业务通知任务；实际外部邮件仍按既有状态和重试机制投递，不以发送失败回滚授权。缺收件人、模板、发送配置的情况保留明确状态及补偿入口，不能悄悄跳过。正常运行时按 C28 的 1 分钟时限处理，具体事件与消费者契约在方案中给出。

## 十一、历史商户与上线兼容

1. 现有商户可能有费率、有绑定、有真实交易，但没有新要求的逐项申请和审批记录，须先盘点。
2. 不能因为部署新功能就把全部历史商户误停，也不能把所有费率覆盖项默认当作已经批准。
3. 历史授权基线应由受控业务确认，标明“历史配置核验/基线登记”等真实来源，不能补造商户申请、审批人或过去审批时间。
4. 新老门禁切换、待核验商户的处理方式、历史授权的有效范围与生效时点是发布前必定稿事项。
5. 保留已发生交易的费用和执行事实；费率或绑定后续变化不能追改历史。
6. 研发阶段必须具备只读盘点、迁移校验、灰度、回退或暂停新增能力的可操作方案，但本轮不执行任何数据变更。
7. 历史观察仅兼容经核验且冻结的历史方式清单；观察期间新增 MID、平台方式或新配置不得顺带增加未批准支付方式。替换同一已允许方式的执行目标继续沿用原配置治理，不能把兼容上限理解成永远不能换 MID。
8. 测试/正式的实际数据隔离作为技术核验项，本轮未形成跨环境同步的业务决定，也不新增环境申请字段或同步能力。
9. 有成功交易及无成功交易的方式均逐项核验。无成功交易时，证据须能还原基线时点的方式启用、费用及有效执行条件，并保存证据引用、适用范围、登记人和复核人；只有当前配置或无法核实当时状态的项目保持待核验。

## 十二、验收标准草案

| 编号 | 前提与操作 | 预期结果 |
|---|---|---|
| A01 | 商户有 Visa 费率，但尚无正式授权 | 方式全景明确未开通，不能因费率直接受理新 Visa 交易 |
| A02 | 商户同时申请 Visa、Mastercard、Apple Pay，平台逐项处理 | 每项独立展示结果，部分拒绝不覆盖已通过项 |
| A03 | 管理人员代某商户申请并尝试自审 | 拒绝自审；有权限且不同人的审批才可生效 |
| A04 | Visa 审批通过但缺少费率/通道 | 商户看见已获准且待配置，管理端能定位全部缺项；交易不可被误放行 |
| A05 | 当前生效费率、通道等齐备 | 只在实际满足的币种、动作与限制范围内呈现可用；原有风控仍可拒绝单笔请求 |
| A06 | 一项能力只有一个有效 MID | 使用固定目标，不要求无意义的多候选策略配置 |
| A07 | 同一渠道两个 MID 均满足相同请求条件 | 识别多个候选并采用明确有效策略；不是“同渠道所以必定固定” |
| A08 | 绑定两条渠道，但分别仅支持不同币种 | 按请求条件分别计算候选，不把每个请求都错误标为多通道 |
| A09 | 同一规则覆盖多个已批准/未批准方式 | 费率覆盖与授权分别显示；ALL 规则不能扩大授权 |
| A10 | 商户查看某方式费率，再从当前费率查看其适用范围 | 规则、版本、生效时间和开通事实一致；不把阶梯/固定费压成单一百分比 |
| A11 | 授权通过后渠道或 MID 停用/到期 | 双端可用情况更新并解释原因；相关新请求不能继续用已失效目标 |
| A12 | 扩围申请被拒绝或撤回 | 原先已生效的合法范围继续存在，不被新申请结果覆盖 |
| A13 | 暂停新收款后处理历史订单后续动作 | 不无条件停掉历史查询/回调等；资金动作仍按原业务权限和状态机判断 |
| A14 | 重复提交、并发审批、旧页面版本或通知重投 | 不重复授权、不覆盖新事实，结果与审计可追溯 |
| A15 | 未授权账号修改商户标识或猜测方式申请编号 | 列表、详情、审批、费率与导出同时受数据范围约束 |
| A16 | 同商户订单有两次独立付款尝试，或同系统订单多次渠道事件 | 各类计数身份可区分；不把所有事件重复计为新交易或静默合并独立尝试 |
| A17 | 钱包交易有已确认底层卡品牌 | 支付方式与卡组织均可分析，整体汇总不重复计数，VAMP 只使用适用口径 |
| A18 | 无欺诈/争议数据或不适用某指标 | 展示缺失/不适用，不伪造 0 或官方监控结论 |
| A19 | 新功能上线遇到无申请记录的历史商户 | 按经确认的基线和过渡策略处理，不根据费率自动批准，也不无差别停用 |
| A20 | 收银台、PayByLink、OpenAPI 展示或提交方式 | 使用一致的授权、费用及执行事实；收银台可展示业务条件满足但前端交互尚未接好的真实方式，预留展示不等于 OpenAPI 或真实付款可执行 |
| A21 | 平台分别存在已启用和未启用支付方式 | 当前申请目录包含全部已启用项，包含非卡方式；未启用项不作为可选申请或意向项展示 |
| A22 | 商户申请某支付方式 | 不要求额外申请币种/地区；后台实际能力限制在查询、展示与受理中继续生效 |
| A23 | MID 同时支持 Visa、Mastercard；商户只获批 Visa | 绑定后仅自动关联 Visa；Mastercard 未获批，不能被自动放行 |
| A24 | 已获批方式的有效 MID、费用及选择条件先后配齐 | 不增加人工逐项启用，自动达到配置就绪；不同配置先后顺序产生一致结果 |
| A25 | 有效 MID 已绑定，但缺费用或候选选择冲突 | 商户后台保留已获批事实并展示缺项，收银台不加入该付款选项，不因自动关联而放行 |
| A26 | 高权限人员发起开通并尝试立即生效或自审 | 必须由另一名有权限人员复核，复核前不产生有效授权 |
| A27 | Apple Pay/Google Pay 满足真实授权、费率和有效 MID 等条件，但前端按钮加载未适配 | 展示真实 Logo/名称及合适的预留容器，说明暂不可付款；商户授权状态保持真实，不能改成未开通 |
| A28 | 某前端钱包组件已存在，但商户未获批该方式 | 收银台仍不展示或放行，不以有组件扩大授权 |
| A29 | 组件未适配、真实组件加载失败或后端执行尚不具备 | 分别按真实状态处理，不无限加载、不伪造按钮/二维码/结果、不发起尚不能执行的支付；不把三者一概归为商户未开通 |
| A30 | 本期复用商户审核、主表、待办等既有结构 | 既有开户/资料审核记录不混入新业务，原编辑不覆盖新准入字段；新增具有明确必要性，关联仍回到同一商户/规范方式/费用版本/MID 与交易事实 |
| A31 | 历史 Visa 商户处于观察模式，新绑支持 Mastercard 的 MID | 仅冻结清单或正式批准范围可继续，未批准 Mastercard 不被兼容例外放行 |
| A32 | 同一链接创建 requestId 改变非卡允许集合，或仅变换集合顺序 | 改变语义返回幂等冲突；等价排序/去重返回原结果；新范围不能匹配旧卡摘要 |
| A33 | 审批业务提交后、邮件任务入库前中断，随后事件重投 | 原事件可恢复并只创建一次业务通知任务；授权不回滚，状态与补偿可查 |
| A34 | 无人工修改，授权/绑定越过自然生效或到期点 | 页面查询重算，新受理即时按有效性校验；正常运行时跟进和通知 1 分钟内处理，不重复产生同次转移通知 |
| A35 | 批准后同时缺费用和 MID，随后配齐并再次退化 | 进入统一待分派，指定/转派沿用权限；来源事实决定自动关闭/重开，人工完成不能伪造就绪 |
| A36 | 同一 URL 两次有效独立提交都在建单前失败；另有同键重放 | 前两次保留不同尝试且真实系统订单关联为空；重放不增独立尝试，纯组件选择不计付款失败 |
| A37 | 只获批 Apple Pay，底层为 Visa 或渠道未返回品牌 | 只检查钱包授权，底层能力由渠道/MID判断；不自动授予直接 Visa，不能把普通卡请求冒充钱包 |
| A38 | 方式获批，既有业务权限和 MID 分别允许/禁止预授权 | 不新增动作审批；允许组合按原规则执行，缺权限或缺能力仍拒绝，历史后续动作沿原状态机 |
| A39 | 首次开通、暂停恢复、终止重新申请、授权到期及有效期调整 | 首次及终止重新申请双人；生命周期操作由授权管理人员单人审计；延期不复活终止项、不解除暂停，到期不等待任务才阻断 |
| A40 | 仅选择真实获准但组件尚未接通方式创建链接 | 允许创建，创建结果和收银台明确当前无法付款；不伪造支付失败/成功，不延长有效期或自动扩大允许范围 |
| A41 | 原 EDC 交易进入本期准入逻辑 | 保持原交互和既有转换规则，费用/双币种事实一致；不擅自新增商户 EDC 开关或报价确认协议 |
| A42 | 交易准备、暂停/终止、授权到期或费用切换并发 | 按最终核验与受理边界得到可复验结果，原幂等恢复不重付，真实多数据源/连接与锁证明未完成不得宣告通过 |
| A43 | 历史方式无成功交易，分别以可核实的历史配置和仅当前配置作为申请纳入材料 | 前者经逐项登记及复核后纳入相应批次；后者保持待核验。重复导入同一批次只保留同一登记结果，暂停、终止或已到期的限制优先 |
| A44 | 授权 12:00 到期，分别验证 11:59:59.900 完成最终检查并于 12:00:00.020 提交、12:00 才检查、到期前检查通过但准备失败 | 第一笔提交成功后继续；第二笔拦截；第三笔无已受理事实，重试必须重新检查权限。已提交请求用原幂等键恢复原结果 |

上述为需求验收定义，尚未运行功能测试或运行环境验收。

## 十三、待确认范围与后续顺序

### 本轮补充确认

1. 第一期仅按具体支付方式申请，币种/地区沿用后台能力限制；不复制截图的消费者地区申请字段。
2. 商户当前申请目录展示平台已启用的所有支付方式，不为未启用项提供申请或意向入口；平台应在具备能力后才启用。
3. 已批准方式在渠道/MID 具备能力、绑定有效且费用和选择条件满足后自动就绪，不额外逐项人工启用。
4. 自动关联不扩大审批范围；Visa 获批不能因 MID 也支持 Mastercard 而顺带获准 Mastercard。
5. v1.4 高权限开通仍需另一名有权限人员复核，不新增单人立即授权例外。
6. 收银台按真实开通方式及基础交易条件显示；前端尚未接入真实钱包按钮加载时保留真实方式的展示及交互预留，不将其解释为商户未开通，也不加入虚构方式。
7. 缺有效费率或候选选择冲突不进入付款选项；仅满足基础条件但付款交互未接好这一类允许预留展示，不允许尚未具备的真实支付提交。
