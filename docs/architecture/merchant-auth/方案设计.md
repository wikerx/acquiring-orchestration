# 商户系统账号激活、邮箱验证与安全找回密码方案

## 技术方案概述

商户系统在复用管理系统安全能力的基础上，增加严格的商户租户边界。匿名找回密码始终使用 `merchantId + loginAccount` 定位商户成员，再回到 `sys_account` 校验账号；不向调用方暴露账号是否存在、邮箱是否可用或 MFA 状态。

商户主账号和员工账号统一改为“待激活账号 + 邮箱所有权验证 + 首次设密”，不再生成、展示或发送明文初始密码。商户管理员重置员工密码时仅签发一次性找回流程，由账号本人完成邮箱验证、MFA 校验和新密码设置。

## 现状与差距

| 范围 | 当前行为 | 目标行为 |
|---|---|---|
| 登录页 | 只有商户号、账号、密码、图形验证码和 MFA | 增加忘记密码入口，保持商户号作为必填身份维度 |
| 主账号开户 | 管理系统生成随机初始密码并通过邮件发送 | 建立待激活账号，邮件只发激活验证码和链接 |
| 员工创建 | 商户管理员输入明文初始密码 | 移除密码字段，由员工激活时首次设密 |
| 管理员重置 | 管理员输入明文密码，邮件再发送临时密码 | 只发起一次性安全重置，不接收和发送明文密码 |
| 个人邮箱 | 商户账号直接替换正式邮箱，仅清空验证时间 | 先校验当前操作人 MFA，写入 `pending_email`，新邮箱验证后再原子切换 |
| 员工邮箱 | 管理员编辑后直接替换，且可能保留旧验证时间 | 写入待验证邮箱，完成所有权验证后才变更可信邮箱 |
| 密码规则 | 后端个人改密已是 12–64 位，但商户页面和管理重置仍是 8 位规则 | 所有入口统一为 12–64 位、大小写、数字、特殊字符、禁止空白、禁止最近 4 个历史密码 |

## 技术选型

| 类别 | 选择 | 理由 |
|---|---|---|
| 后端 | Spring Boot + MyBatis-Plus + 现有认证组件 | 不引入新框架，复用 `SystemAuthService`、MFA、会话注销和密码历史能力 |
| 前端 | Vue 3 + TypeScript + Element Plus | 与 `merchant-portal` 现有登录页和表单体系保持一致 |
| 持久化 | 复用 `sys_password_reset_request` 和 `sys_email_verification_request` | 两张表已以 `app_id` 区分应用，适合扩展为系统级账号安全请求表 |
| 分布式限流 | 现有 Redis 滑动窗口 | 跨实例原子限流，数据库计数保留审计型第二道保护 |
| 邮件 | 现有模板、路由、发送记录和 SMTP 队列 | 确保管理系统仍能查看商户邮件发送记录和失败原因 |

## 架构设计

```text
merchant-portal
  -> /merchant/auth 公开认证接口
  -> MerchantAuthApplicationService
  -> MerchantPasswordResetService / MerchantEmailVerificationService
  -> 共享认证 Mapper、MFA、密码历史、会话注销
  -> sys_password_reset_request / sys_email_verification_request
  -> MerchantTemplateEmailService -> msg_email_record -> SMTP

service-admin
  -> AdminMerchantPrimaryAccountProvisioningService
  -> 创建商户主账号的待激活请求
  -> AdminEmailService -> 同一邮件记录体系
```

`service-merchant` 不依赖 `service-admin`。原来仅存放在 `service-admin` 的请求 DO/Mapper 下沉到 `component-db` 作为共享持久化契约；Admin 和 Merchant 仍各自保留流程编排、账号定位策略和邮件模板选择。

## 核心流程

### 商户主账号和员工账号激活

1. 创建账号时写入不可对外使用的高熵占位密码，设置 `activation_status=PENDING_ACTIVATION`、`email_verified_at=NULL`。
2. 创建 30 分钟有效的邮箱验证请求，邮件发送 6 位大小写敏感的字母数字验证码和高熵 `requestId` 链接。
3. 验证码通过后签发 5 分钟、只能消费一次的 `actionToken`。
4. 用户设置首次密码，事务内写入密码、激活时间和邮箱验证时间，再进入正常登录与 MFA 绑定。
5. `PENDING_ACTIVATION` 账号不能登录，且不进入匿名找回密码真实流程。

### 匿名找回密码

1. 用户填写商户号、登录账号和图形验证码。
2. 服务端先消费图形验证码，再按 `merchantId + loginAccount` 查询 `sys_merchant_user`，校验返回的 `account_id` 确实属于 MERCHANT 应用和该商户。
3. 停用、锁定、待激活、邮箱未验证或不存在的账号均写入虚拟请求，返回与真实账号一致的结构和文案。
4. 邮箱验证码 30 分钟有效；验证成功后，已绑定 MFA 的账号必须继续校验 TOTP。未正常绑定 MFA 的账号不降级为邮箱单因素重置，改为联系商户管理员或平台支持。
5. 邮箱和 MFA 都通过后签发 5 分钟一次性 `resetToken`，最终设置符合统一策略的新密码。
6. 重置成功后记录密码历史，原子消费令牌，注销该账号全部旧会话，发送不含密码的安全通知。

### 邮箱变更

1. 当前用户在个人中心修改邮箱时，必须同时提交当前 TOTP 验证码。
2. 待验证新邮箱只写入 `pending_email`，验证前正式邮箱、`email_verified_at` 和找回密码收件地址均不变。
3. 商户管理员在员工管理中修改邮箱时也使用待验证流程，禁止直接把新地址标记为可信。
4. 邮箱验证成功后事务内替换 `sys_user.email` 和 `sys_account.email`，写入新的 `email_verified_at`，清空 `pending_email`。

## 接口设计

| 方法 | 路径 | 认证 | 用途 |
|---|---|---|---|
| POST | `/merchant/auth/password-reset/request` | 公开 + 图形验证码 | 使用 `merchantId + loginAccount` 发起匿名找回 |
| POST | `/merchant/auth/password-reset/email/verify` | 公开 + 邮箱码 | 校验邮箱验证码并进入 MFA 阶段 |
| POST | `/merchant/auth/password-reset/mfa/verify` | 公开 + 阶段令牌 | 校验 TOTP 并签发重置令牌 |
| POST | `/merchant/auth/password-reset/confirm` | 公开 + 重置令牌 | 原子设置新密码并注销旧会话 |
| POST | `/merchant/auth/email-verification/verify` | 公开 + 邮箱码 | 验证账号激活或邮箱变更请求 |
| POST | `/merchant/auth/account-activation/complete` | 公开 + 动作令牌 | 首次设密并完成激活 |
| POST | `/merchant/system/accounts/{id}/email-verification/send` | 商户权限 | 重发员工激活或邮箱验证邮件 |
| POST | `/merchant/system/accounts/{id}/reset-password` | 商户权限 | 发起员工安全重置，请求体不再包含密码 |

上述公开接口加入 `MerchantAuthWebMvcConfig` 白名单，但每个阶段均有独立限流、高熵请求号、哈希令牌、失败次数和有效期校验，白名单不代表无安全校验。

## 数据模型

### 复用并扩展的表

| 表 | 调整 | 索引与约束 |
|---|---|---|
| `sys_account` | 商户账号使用现有 `pending_email`、`email_verified_at`、`activation_status`、`activated_at` | 继续以 `app_id` 和账号主键隔离；登录必须另校验 `merchant_id` |
| `sys_password_reset_request` | 表语义从“管理后台”改为“系统账号”，增加可空 `merchant_id` 作为商户审计和二次边界校验 | 保留 `request_no` 唯一索引；增加 `(app_id, merchant_id, account_fingerprint, created_at)` 和 `(app_id, merchant_id, account_id, state, created_at)` |
| `sys_email_verification_request` | 增加可空 `merchant_id`，复用 `purpose` 区分 `ACCOUNT_ACTIVATION`、`EMAIL_VERIFICATION`、`EMAIL_CHANGE` | 保留 `request_no` 唯一索引；增加 `(app_id, merchant_id, account_id, state, created_at)` |
| `msg_email_template` | 新增商户中英文安全模板 | 沿用现有模板唯一约束和版本管理 |
| `msg_email_record` | 不新增表，所有真实发送和准备失败都必须留记录 | 继续使用商户号、业务类型和业务号查询 |

`account_fingerprint` 对商户流程使用规范化后的 `merchantId + "\n" + loginAccount` 计算 SHA-256，不在限流索引中存放明文登录账号。

## 账号状态展示

| 字段 | 含义 | 对登录的影响 |
|---|---|---|
| `status` | 业务启停状态 | 停用时不允许登录 |
| `activationStatus` | 是否已完成首次邮箱验证和设密 | `PENDING_ACTIVATION` 不允许登录 |
| `emailVerificationStatus` | 当前正式邮箱是否已验证 | 未验证时不允许匿名找回密码 |
| `pendingEmail` | 正在等待所有权验证的新邮箱 | 验证前不用于登录通知或找回密码 |
| `mfaStatus` | MFA 绑定、启用、锁定或豁免状态 | 决定登录和找回密码的第二因素步骤 |

## 邮件模板

新增下列模板的 `zh-CN` 和 `en-US` 版本，颜色、字体、按钮和信息区块沿用 Vexra 蓝白基础，商户应用标识使用 `Vexra Merchant`：

- `MERCHANT_ACCOUNT_ACTIVATION`：主账号或员工账号激活。
- `MERCHANT_EMAIL_VERIFICATION`：已激活账号验证邮箱或修改邮箱。
- `MERCHANT_PASSWORD_RESET_VERIFY`：自助或商户管理员发起的密码重置验证。
- `MERCHANT_PASSWORD_RESET_SUCCESS`：密码重置成功通知，不包含新密码。

将 `MERCHANT_ACCOUNT_CREATED` 和 `MERCHANT_PASSWORD_CHANGED_BY_ADMIN` 标记为停用的历史模板，保留旧记录可追溯性，不删除历史数据。验证码是敏感变量，邮件记录和日志不得存储或打印其明文。

## 关键安全决策

| 决策点 | 选择 | 理由 |
|---|---|---|
| 商户身份 | `merchantId + loginAccount` | 同一登录名可在不同商户内出现，必须防止跨商户找回 |
| 主账号内部登录名 | 新建主账号与员工一样使用商户后缀存储，`sys_merchant_user.login_account` 保留页面登录名 | 避免同一联系邮箱无法用于多个商户主账号 |
| 验证码 | 6 位且同时包含大写、小写和数字，大小写敏感，30 分钟有效 | 与已确认的管理系统规则一致 |
| 令牌 | 仅返回原文，数据库只存 SHA-256，5 分钟有效，单次消费 | 降低数据泄漏和重放攻击风险 |
| 并发 | 最终确认使用 `SELECT ... FOR UPDATE` 或等价条件更新 | 防止同一重置令牌并发消费两次 |
| 限流 | 申请、邮箱验证、MFA 验证、最终确认分别使用独立 IP 窗口，申请再增加账号指纹窗口 | 避免某一阶段的容量被其他阶段消耗，同时抑制对单账号的攻击 |
| 邮件失败 | 真实账号的手工发起操作在邮件准备失败时返回失败，且必须生成失败记录 | 避免页面显示成功但没有任何发送记录 |
| 匿名失败 | 对用户仍返回统一文案，内部记录可观测的失败原因 | 防止账号枚举，同时保证运维可追查 |

## 前端交互设计

保留现有商户登录页蓝绿品牌和左右布局，不重做登录视觉系统。在登录卡片内增加“忘记密码”文字操作，找回、激活和邮箱验证页继续使用同一品牌外壳、紧凑步骤状态和 6 格验证码输入。

页面不展示“验证码包含大小写和数字”这类后端生成规则，只显示有效期、重新发送倒计时和当前需要完成的动作。所有状态、错误和成功文案同步补齐中英文 i18n。

商户员工管理页移除“初始密码”和“输入新密码”弹窗，将操作改为“发送激活邮件”、“发送密码重置邮件”，并增加激活状态、邮箱验证状态和待验证邮箱的列表、筛选和详情展示。

## 兼容性、回滚与暂不处理

- SQL 使用幂等方式新增可空字段和索引，不删除现有列、历史请求或邮件记录。
- 历史已激活商户账号不批量修改密码、激活状态或邮箱验证时间；邮箱可信性需根据真实业务数据单独确认。
- 后端与前端必须同步发布，因为员工创建和重置密码请求体会移除明文密码字段。
- 本期不将浏览器 Token 从 `localStorage` 迁移到 HttpOnly Cookie；这是独立认证架构升级，不与本次商户账号流程捆绑。
- 本期不把 Admin 和 Merchant 的完整业务编排抽象成单一通用服务；只下沉共享持久化契约和密码安全能力，避免租户规则被过度抽象隐藏。
