# 支付收单系统工程约束

## 1. 文档定位

本文是 `acquiring-orchestration` 与 `acquiring-frontend` 作为完整支付收单平台协作时必须遵守的工程约束。

本文优先级高于一般代码风格偏好。涉及资金、安全、状态、幂等、清结算、敏感数据时，应按本文执行。

## 2. 当前能力边界

当前系统已经具备的基础能力：

1. Spring Cloud 多模块服务框架。
2. 商户 OpenAPI JWT 鉴权、请求体解密、响应 `data` 加密、Redis `jti` 防重放。
3. 后台管理和商户后台登录、菜单、角色、权限基础能力。
4. 商户 OpenAPI 安全材料生成与查询基础能力。
5. Redis、RocketMQ、MyBatis Plus、ISO 国家币种、分表治理等公共能力。
6. 前端后台管理、商户后台、Hosted Checkout 的基础应用框架。

当前系统尚未具备完整生产交易核心能力：

1. `service-payment` 仍是收单支付模拟实现。
2. `service-payout` 仍是代付模拟实现。
3. 未落地正式支付交易主单、操作单、资金幂等表、渠道流水、状态机和清结算模型。
4. 未实现完整 SALE、AUTH、CAPTURE、REFUND、VOID、REVERSAL、DISPUTE 交易闭环。
5. Hosted Checkout 尚未接入真实 checkout session、支付提交和结果查询链路。

所有后续文档、接口、页面和代码都不得把当前模拟实现描述为已具备生产资金处理能力。

## 3. 核心原则

1. 资金安全优先于代码整洁。
2. 状态一致优先于接口简单。
3. 数据库唯一约束优先于单纯 Redis 幂等。
4. 交易状态机必须显式、单向、可审计。
5. 渠道原始状态不能直接暴露为平台状态。
6. 商户可见错误、付款人可见错误、后台内部错误必须分层。
7. 前端不得自行创造支付、退款、结算、风控状态。
8. OpenAPI 接入层不得承载支付核心逻辑。

## 4. 模块边界约束

### 4.1 `service-openapi`

允许：

1. JWT 鉴权。
2. 请求解密。
3. 参数校验。
4. `jti` 防重放。
5. 商户基础状态和权限校验。
6. 响应 `data` 加密。
7. 调用 `service-payment` 和 `service-payout`。

禁止：

1. 直接落支付交易主单。
2. 直接完成渠道扣款或退款。
3. 维护平台交易状态机。
4. 绕过 `@VerificationAndProcessing` 新增商户对外接口。
5. 打印完整请求明文、JWT、密钥、卡号、CVV。

### 4.2 `service-payment`

目标职责：

1. 支付交易主单。
2. 交易操作单。
3. 授权、请款、撤销、冲正、退款。
4. 渠道路由与渠道调用编排。
5. 渠道请求、响应、回调记录。
6. 交易状态机。
7. 资金幂等控制。
8. 交易事件发布。
9. 对账、清分、结算所需基础数据。

当前限制：

1. 不要继续在 `PaymentTransactionServiceImpl` 模拟实现中堆正式交易逻辑。
2. 新能力应围绕应用服务、交易状态机、幂等服务、仓储服务、渠道调用服务逐步小步补齐。

### 4.3 `service-payout`

目标职责：

1. 代付申请。
2. 代付审核。
3. 代付渠道路由。
4. 代付状态机。
5. 渠道回调。
6. 退汇处理。
7. 幂等控制。
8. 代付流水与账务状态。

当前限制：

1. 不要继续在 `PayoutTransactionServiceImpl` 模拟实现中堆正式代付逻辑。
2. 代付审核、渠道状态和账务状态必须分层设计。

### 4.4 `component-library`

只放跨服务基础能力：

1. 统一返回模型。
2. 基础异常。
3. Web 通用配置。
4. Redis、MQ、DB 基础封装。
5. 安全加密与 JWT 工具。
6. ISO 字典能力。

禁止放入：

1. 具体支付交易规则。
2. 某个渠道的私有业务规则。
3. 某个后台页面的私有规则。
4. 商户侧个性化交易逻辑。

### 4.5 `channel-library`

只放渠道适配抽象和通用渠道模型。

禁止：

1. 平台交易状态机。
2. 商户业务规则。
3. 管理后台规则。
4. 直接暴露渠道原始响应给商户。

## 5. 交易链路约束

### 5.1 支付创建

必须具备：

1. 商户身份。
2. 商户订单号。
3. 请求唯一标识。
4. 支付操作类型。
5. 金额、币种、币种精度。
6. 请求体安全摘要。
7. 数据库幂等记录。
8. 交易主单。
9. 状态流转记录。

幂等维度：

```text
merchantId + merchantOrderNo + operationType
```

### 5.2 授权

授权成功只代表资金冻结或授权完成，不代表应结金额完成。

必须记录：

1. 授权金额。
2. 授权币种。
3. 授权有效期。
4. 渠道授权号。
5. 可请款金额。
6. 可撤销金额。

### 5.3 请款与增量请款

必须校验：

1. 原授权状态必须允许请款。
2. 请款金额不能超过可请款金额。
3. 增量请款必须确认渠道和卡组织支持。
4. 每次请款必须形成独立操作单。

### 5.4 退款

必须校验：

1. 原交易存在且已成功请款或销售成功。
2. 退款币种与原交易一致或有明确换汇规则。
3. 累计退款金额不能超过可退金额。
4. 商户退款单号必须全局幂等。

建议幂等维度：

```text
merchantId + merchantRefundNo
merchantId + originalTransactionId + operationType + merchantRefundNo
```

### 5.5 撤销与冲正

撤销用于取消未清算授权，冲正用于异常链路恢复。二者不能混用。

必须记录：

1. 原交易号。
2. 原操作单号。
3. 发起原因。
4. 渠道请求与响应。
5. 最终状态。

### 5.6 拒付

拒付不是退款。拒付必须独立建模，至少记录：

1. 原交易号。
2. 拒付案件号。
3. 卡组织或渠道原因码。
4. 争议金额与币种。
5. 证据提交状态。
6. 最终输赢状态。

## 6. 状态机约束

必须做到：

1. 平台交易状态使用枚举。
2. 渠道原始状态单独保存。
3. 状态更新带当前状态条件。
4. 终态不可逆。
5. 所有状态流转写入状态流转记录。
6. 失败原因按商户、付款人、后台内部分层。

禁止：

1. 散落手写 `"SUCCESS"`、`"FAILED"`、`"RECEIVED"` 等状态字符串。
2. 无条件 `update status = ? where id = ?`。
3. 渠道回调直接覆盖平台终态。
4. MQ 重复消费覆盖终态。

## 7. 幂等约束

资金类幂等必须以数据库唯一约束兜底，Redis 只能作为前置保护或短期防抖。

必须具备幂等的操作：

1. 创建支付。
2. 授权。
3. 请款。
4. 撤销。
5. 冲正。
6. 退款。
7. 创建代付。
8. 代付审核。
9. 渠道回调。
10. 商户通知。
11. 对账入账。
12. 清分。
13. 结算。
14. MQ 消费。

建议幂等键：

```text
merchantId + merchantOrderNo + operationType
merchantId + transactionId + operationType
merchantId + merchantRefundNo
channelCode + channelOrderNo + callbackType
messageId + consumerGroup
settlementBatchNo + merchantId
```

## 8. 金额、币种和汇率约束

金额规则：

1. Java 业务金额使用 `BigDecimal`。
2. 数据库存储必须明确主币种单位、最小单位或高精度 decimal。
3. 禁止使用 `double` / `float` 处理金额、费率、汇率。
4. 禁止默认所有币种都是两位小数。
5. 禁止在不知道币种精度时直接 `movePointRight(2)`。

币种规则：

1. 使用 ISO 4217 三位币种码。
2. 交易金额、授权金额、请款金额、退款金额、手续费、保证金、结算金额必须分开。
3. 多币种汇总必须按结算币种分组。

汇率规则：

1. 交易汇率、结算汇率、查询展示汇率、清分汇率必须区分。
2. 汇率至少保留 8 位以上小数精度。
3. 汇率来源、生效时间、使用场景必须留痕。

## 9. OpenAPI 安全约束

商户对外接口必须：

1. 使用 `POST`。
2. 使用 `/api/rest/{domain}/{version}` 路径。
3. 使用 `@VerificationAndProcessing`。
4. 经过 JWT 验签。
5. 经过请求体解密。
6. 经过参数校验。
7. 经过 `jti` 防重放。
8. 成功响应 `data` 加密。

生产和 UAT 环境：

```text
openapi.security.replay.required=true
```

禁止：

1. 返回未加密的成功 `data`。
2. 打印完整请求明文。
3. 打印 JWT、merchantKey、私钥、API Key。
4. 让 OpenAPI 层直接处理渠道扣款和交易状态机。

## 10. 渠道回调约束

渠道回调不能套用商户 OpenAPI 的 `@VerificationAndProcessing`，但必须有独立安全机制。

必须具备：

1. 渠道维度签名校验。
2. 渠道 IP 白名单。
3. 回调原文保存。
4. 回调幂等。
5. 渠道订单号与平台订单号映射。
6. 金额、币种、状态校验。
7. 状态机合法流转校验。
8. 异常回调告警。

## 11. 内部接口约束

所有 `/internal/**` 接口必须明确内部调用边界。

允许方式：

1. 内部服务 token。
2. 服务间签名。
3. mTLS。
4. 内网网关隔离。
5. Nacos 内网访问限制。
6. IP 白名单。

禁止认为路径叫 `/internal/**` 就天然安全。

当前 `service-payment` 和 `service-payout` 的内部创建接口应优先补充内部调用鉴权或明确只允许内网访问。

## 12. MQ 与事务约束

禁止：

1. 先发 MQ 后提交本地事务。
2. 先通知商户后提交本地事务。
3. MQ 重复消费导致重复扣款、重复退款、重复入账。

建议：

1. 本地事务 + 事件表。
2. 事务提交后异步发 MQ。
3. 消费端以 `messageId + consumerGroup` 幂等。
4. 终态保护必须在数据库状态机层兜底。

## 13. 前端约束

后台管理：

1. 使用后端菜单动态生成路由。
2. 前端权限码与后端 `@RequiresPermission`、数据库 `sys_permission` 保持一致。
3. 敏感密钥默认只展示摘要和指纹。
4. 日期时间展示统一为 `yyyy-MM-dd HH:mm:ss`。

商户后台：

1. 不得越权展示其他商户数据。
2. 商户菜单必须来自后端授权结果。
3. 交易、退款、结算页面不得自行推导资金状态。

Hosted Checkout：

1. 不得在前端持久化 PAN、CVV、PIN。
2. 支付金额、币种、订单号必须来自后端 checkout session。
3. 前端只能展示后端授权的支付方式。
4. 支付结果必须以后端查询或回调状态为准。

## 14. 设计评审触发条件

以下变更必须先做设计评审：

1. 新增支付方式。
2. 新增渠道。
3. 修改交易状态机。
4. 修改资金幂等键。
5. 修改退款、撤销、冲正规则。
6. 修改金额、币种、汇率、手续费规则。
7. 修改清分、结算、对账规则。
8. 修改 OpenAPI 加密、签名、JWT、防重放。
9. 修改核心资金表结构。
10. 新增渠道回调入口。
