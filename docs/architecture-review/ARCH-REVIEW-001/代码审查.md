## 问题清单

### 严重问题

1. dev 尚未具备代码要求的 `sys_mq_outbox` 表结构，启动期 Relay 查询触发 `BadSqlGrammarException`。这是启用通用可靠 MQ、异步操作/登录日志和异步邮件前的 P0 数据库门禁；仓库 SQL 目前只是版本化草案，未经确认不得执行。
2. SDK dev 探针返回 `F409 Merchant config not found`，无法发起一笔具备有效商户身份的支付写入并串联缓存、分片、渠道、Outbox、Data 通知和查询。不得绕过鉴权或伪造商户配置完成验收。
3. 未跟踪的历史数据库导出包含不应进入版本库的运行数据和敏感字段。在纳入 Git 前必须由数据所有者移出仓库或完成受控脱敏；本轮没有自动重写该用户文件。
4. Admin 预览可以渲染登录页且控制台无错误，但详情浏览器复跑受登录和图形验证码阻断；没有把历史页面结果当成本轮新鲜证据。

### 建议修改

1. 邮件 `processingTimeoutSeconds` 的默认值大于当前常用 SMTP 超时，但账户级连接/读取超时与恢复窗口之间缺少启动期硬校验，配置错误时可能并发恢复仍在发送的邮件。
2. SMTP 没有业务幂等协议。发送成功后、数据库成功状态落库前进程崩溃，恢复任务可能再次发送；文档、监控和运营处置必须按 at-least-once 语义设计。

### 代码复审结论

- 详情链路直接使用列表和数据库返回的 `transactionDateTime`、`rootTransactionDateTime`；详情和支付写链路不再解析交易号。解析器只保留给内部异步恢复和动作列表补充查询。
- 17 个交易 Mapper 共 89 条 Select、21 条 Update、12 条 Insert；动态物理交易表名、Risk 交易 `UNION ALL` 和交易 `@DS(MASTER/SLAVE)` 均为 0。
- 可靠发布器不会再无条件吞掉重复事件号；只有 Topic、Tag、生产服务和稳定业务载荷一致时才允许幂等重放。
- Admin/Merchant 操作日志、登录日志、风险/安全审计和邮件具备 Outbox/CAS 代码边界。商户/渠道请求响应及交易流程记录属于交易事实，继续与交易状态同事务持久化。
- 日志收口不再输出底层异常消息；注释说明了分片时间、幂等、CAS、SMTP 重复窗口和事务边界。
