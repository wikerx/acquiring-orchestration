# 收单支付链接部署与验收约束

本文对应 `docs/architecture/payment-link-design.md` 的首批决策。支付链接不走代付，不开启人工复核，不新增多次成功、付款人改金额、草稿、停用恢复或访问趋势。

## 配置与环境

| 项目 | dev | test | uat / prod |
| --- | --- | --- | --- |
| 默认入口 | 关闭 | 关闭 | 关闭 |
| 表结构 | 独立验收库通过后迁移开发库 | 使用环境自身 MySQL 预检 | 由环境迁移流程执行，禁止复制开发库 |
| 托管地址 | HTTPS 或本机回环 HTTP origin | 环境自身 HTTPS origin | 环境自身 HTTPS origin |
| 签名密钥 | 本机受控文件生成，不能提交 | Secret 注入独立随机密钥 | Secret 注入及轮换，不能复用 Checkout pepper 或内部 HMAC |
| 内部授权 | service-payment 模板已补最小调用范围 | 按相同契约配置本环境 Nacos | 同左，禁止跨环境密钥 |
| 邮件验收 | 虚构地址与本机 SMTP sink | 测试 SMTP / 指定测试收件人 | 经本环境既有邮件配置与发布流程接入 |

仓库目前仅维护服务专属 `*-dev.yaml`；其他环境沿用自己的 Nacos DataId。新增 `payment.link.*` 缺省关闭，不要求已有环境立即配置密钥。只要开启入口，就必须同时满足存储就绪、有效 origin、活动版本和至少 32 字节的专用签名密钥。

本地生成配置：

```bash
python3 scripts/bootstrap-payment-link-config.py --output /受控目录/payment-link-local.properties --origin http://localhost:5175
```

脚本拒绝覆盖已有文件、权限为 `0600`、不在终端输出密钥，生成后仍保持关闭。将文件通过 Spring `additional-location` 或 Secret 挂载加载，不把文件放进 Git。

## 迁移和开启次序

1. 备份目标库的表结构与相关授权配置，核对当前环境与 schema。预检 `payment_checkout_session`、`payment_checkout_attempt`、`sys_*`、`msg_email_template` 的现有列与索引；确认新表由 `master` 访问、与 Checkout 位于同一业务库。DDL 使用当前 MySQL 8 Checkout 的 `utf8mb4_0900_ai_ci`；若目标表排序规则不同，先评审对齐方案，禁止混合排序规则上线后再绕过 JOIN 错误。
2. 执行 `docs/sql/20261117_01_payment_link_schema.sql`、`20261117_02_payment_link_mail.sql`、`20261117_03_payment_link_permissions.sql`。脚本只增量建立本功能对象，重复执行不新增模板副本或覆盖已有自定义模板。
3. 验证五张领域表、两张邮件请求表、订单与请求唯一索引。核对 Admin / Merchant 菜单、动作权限、默认管理员与商户授权；受限角色继续按现有授权页面配置。
4. 同步内部鉴权调用范围。Payment 只允许 OpenAPI 调用精确的 `resolve` / `start`；Admin / Merchant 使用各自签名身份和服务端操作者范围。Data 只获得两端专用 `export-page`，不能发起链接写操作。
5. 支付域配置 `payment.link.storage-ready=true`，完成相关服务发布。然后设置 origin、active-key-version 和专用 signing-keys，最后设置 `payment.link.enabled=true`。启用参数不依赖前端隐藏按钮保证安全。
6. 双端菜单由后端授权返回；主列表使用各自 StandardTable、编辑列入口、i18n 与时间组件。清理/刷新既有权限缓存并重新获取登录态后核对菜单，不手工给浏览器补业务菜单。

生产网关/静态站点必须将 `/l/*` 和现有 `/checkout/*` 路由到托管应用。公开 HTML/API 配置 `Cache-Control: no-store` 与 `Referrer-Policy: no-referrer`；屏蔽完整 `/l/<凭据>`、`/checkout/<凭据>/...` 在访问日志、APM、统计平台中的原文。不能给这些路径启用第三方统计脚本。二维码在本地生成，不把完整 URL 发往外部服务。

## 一致性与数据边界

- 链接金额沿用核心 `DECIMAL(20,6)` 输入范围，再按 ISO 小数位严格校验。前端持有字符串，不用浮点做财务决定。
- 链接生命周期为 ACTIVE / DISABLED / EXPIRED / COMPLETED；完成来自既有 Checkout 成功事实，到期由服务器当前时间实时判定，不依赖定时任务准点触发。处理中属于支付状态。
- 商户+创建请求号、商户+订单号、链接+收款目标、链接+Checkout 绑定均有数据库唯一约束。已有链接命中原请求返回既有详情；其他重复订单冲突。已有核心交易或 Checkout 会话的订单不能另建链接。
- 失败重试沿用原链接、收款目标和稳定 Checkout 创建请求号。是否仍可开始复用既有收银台判定。成功、处理中与不可继续状态不能签发新的付款入口。跨入口支付最终仍由既有商户订单流原子约束保护，禁止仅靠前端状态决定扣款。
- 新付款准备事务检查链接行锁；停用使用同一行锁与版本 CAS。新请求停用后被拒绝，已有尝试重放、3DS 回跳、查单和结果收敛继续。
- 邮件请求指纹先在独立事务提交，外层持有发送请求行锁。恢复读取使用独立新快照，避免 REPEATABLE READ 旧快照遗漏已提交邮件；再调用既有邮件独立事务准备 Outbox。重试不能换收件人、语言或目标链接。SMTP 层仍遵循现有至少一次投递语义。
- 匿名入口按可信来源 IP 与链接摘要独立限流，默认每分钟查询各 120 次、开始各 20 次，不套用商户 IP 白名单或未经认证的转发头。浏览器处理中默认 5 秒只读查询，错误退避到 30 秒，连续 8 次失败停止自动查询；隐藏标签页暂停，返回页面重新确认，到期按服务端时间自动刷新。
- 邀请邮件按单收件人发送，独立频控：同商户收件人默认 60 秒一次，商户与操作者每小时默认各 100 次；仅本功能生效。状态 4 为等待重试，3 / 5 为关闭 / 取消，不能把“受理”写成“客户已收到”。
- Admin 邀请正文显式启用 HTML 变量转义，主题仍为纯文本；Merchant 沿用已有转义。普通邮件旧调用缺省行为兼容。完整链接是敏感模板变量，正文加密保存，普通投影和导出不返回链接。
- 导出固定任务类型 ADMIN_PAYMENT_LINK / MERCHANT_PAYMENT_LINK，冻结当前账号与商户范围，由下载中心按既有归属领取。文件只有安全白名单列，不含 URL、令牌、客户邮箱或邮件正文。

## 验收门槛

自动化覆盖金额/币种/有效期，幂等请求冲突，同订单唯一性与并发，状态派生、商户隔离，停用后新提交阻断、重复尝试继续回放，匿名接口字段约束/缓存，邮件重放/响应丢失/限流，导出白名单和冻结范围。H2 Mapper 验证使用仓库 DDL，不替代目标 MySQL 的迁移与事务验收。

页面验收需要区分虚构响应自动化与真实后台：双端创建、详情、收款订单/支付尝试、停用、复制/本地二维码、邮件和下载中心；中英文、主题、桌面/窄屏、编辑列恢复；托管链接的有效、无效、过期、处理中、成功及失败重试。真实联调仅使用既有 Mock / 指定沙箱与虚构卡数据，不能把本地测试描述成真实收款或真实外部邮件投递。
