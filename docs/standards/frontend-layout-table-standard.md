# Vexra 管理系统菜单与表格统一交互规范及历史页面整改执行方案

> **适用范围**：Vexra Admin 管理后台、Merchant 商户系统，以及后续采用同一前端框架的管理端系统。
> **文档用途**：作为 Codex 后续前端开发、历史页面整改、功能验收、自测回归的统一执行依据。
> **核心目标**：统一菜单、布局、表格交互，解决长菜单名称、表格字段过多、列宽不可调、字段不可自由显示隐藏、顶部菜单三级菜单缺失等问题。

---

## 0. Codex 执行总指令

请在执行任何代码修改前，先完整阅读本文件，并将本文件作为本次及后续管理端前端开发的强制约束。

本次任务包含两类内容：

1. **统一规范建设**
   - 左侧菜单宽度拖拽；
   - 菜单长名称省略与 Tooltip；
   - 菜单纵向滚动；
   - 侧边菜单与顶部菜单能力一致；
   - 顶部菜单支持三级及以上菜单；
   - 表格内部横向滚动；
   - 表格列宽拖拽；
   - 表格右上角“编辑列”；
   - 列显示隐藏；
   - 列顺序调整；
   - 列宽、列显示、列顺序用户偏好持久化。

2. **历史页面统一整改**
   - 扫描当前 Admin / Merchant 前端项目中所有标准列表页面；
   - 优先抽象公共组件或 Hook；
   - 先完成试点页面；
   - 验证通过后批量迁移历史页面；
   - 后续新增列表页必须自动遵循本规范。

涉及前端交互、布局、页面视觉一致性时，必须使用：

```text
$frontend-design
```

执行前必须先输出实施方案、影响范围、修改文件预估、风险点和测试计划。未经确认，不要直接批量修改历史页面。

## 1. 需求背景

当前 Vexra 管理系统存在以下问题：

1. 左侧菜单层级较深，菜单名称较长时，菜单文字被截断，用户无法完整查看。
2. 当前左侧菜单虽然支持三级菜单，但顶部菜单模式没有同步支持三级菜单，导致切换至顶部菜单后，`收单风控` 下的三级菜单无法展示和打开。
3. 表格字段较多时，列宽固定，长字段展示不完整。
4. 用户无法自由调整表格每一列宽度。
5. 用户无法选择只显示自己关心的字段。
6. 不同列表页面表格实现方式不统一，后续开发容易出现重复实现、样式不一致、交互不一致的问题。
7. 历史页面已存在多个列表页，需要一次性建立统一规范，并逐步整改为相同标准。

## 2. 总体目标

本次改造完成后，需要达到以下目标：

| 目标 | 说明 |
|---|---|
| 菜单统一 | 侧边菜单和顶部菜单使用同一份菜单树数据，同步支持三级及以上菜单 |
| 菜单可用性 | 侧边菜单支持宽度拖拽，长菜单名称支持省略和 Tooltip |
| 表格统一 | 标准列表页统一使用公共表格能力，不允许页面级重复实现 |
| 字段可读 | 表格字段过多时支持内部横向滚动，不强行压缩到不可读 |
| 列宽可调 | 用户可拖动表头边界调整列宽 |
| 字段可控 | 用户可通过“编辑列”控制字段显示隐藏和顺序 |
| 偏好持久化 | 菜单宽度、列宽、列显示、列顺序按用户和表格维度保存 |
| 安全稳定 | 缓存异常不白屏，权限字段不泄漏，业务功能不受影响 |
| 可验收 | Codex 完成后必须按照本文验收标准自测并输出测试结果 |

## 3. 核心原则

### 3.1 公共能力优先

菜单拖拽、顶部菜单递归渲染、表格横向滚动、列宽调整、编辑列、用户偏好缓存必须封装为公共组件、公共 Hook 或公共工具。

禁止在每个业务页面复制一套实现。

### 3.2 配置驱动

业务页面只负责声明：

- 表格唯一标识 `tableKey`；
- 列唯一标识 `columnKey`；
- 列标题；
- 默认宽度；
- 最小宽度；
- 是否可隐藏；
- 是否可拖动；
- 是否固定；
- 默认显示状态；
- 默认排序位置；
- 字段权限。

公共表格组件负责：

- 渲染；
- 横向滚动；
- 列宽拖拽；
- 显示隐藏；
- 顺序调整；
- 配置保存；
- 配置恢复；
- 配置兼容；
- 异常降级。

### 3.3 不破坏现有业务

本次整改不得影响：

- 查询；
- 重置；
- 分页；
- 排序；
- 筛选；
- 新增；
- 编辑；
- 删除；
- 批量操作；
- 导入；
- 导出；
- 多选；
- 固定列；
- 权限控制；
- 路由跳转；
- 页签打开；
- 面包屑；
- 菜单折叠；
- 国际化；
- 暗色/亮色主题，如项目已支持。

### 3.4 用户偏好隔离

布局和表格偏好至少按以下维度隔离：

```text
系统 + 用户 + 表格/页面
```

不同用户、不同系统、不同表格之间不得共用同一份配置。

### 3.5 安全优先

编辑列只是用户展示偏好，不是权限控制机制。

必须保证：

- 用户无权限的字段不得出现在表格列定义中；
- 用户无权限的字段不得出现在“编辑列”面板中；
- 不得通过编辑列功能暴露完整卡号、密钥、证书、私钥、公钥等敏感字段；
- 后端接口仍应负责数据权限和敏感字段脱敏；
- 导出字段不得默认跟随编辑列显示状态，除非业务明确要求；
- 本次不得修改任何业务接口返回结构。

## 5. 菜单统一规范

### 5.1 菜单模式

管理系统支持两种菜单模式：

1. **侧边菜单**；
2. **顶部菜单**。

两种模式必须使用同一份菜单树数据，不能分别维护两套菜单结构。

要求：

- 菜单权限一致；
- 菜单层级一致；
- 路由跳转一致；
- 菜单高亮一致；
- 页签打开一致；
- 面包屑展示一致；
- 不得出现侧边菜单可见、顶部菜单不可见的情况。

## 6. Bug 修复：顶部菜单支持三级及以上菜单

### 6.1 当前问题

当前系统侧边菜单已经支持三级菜单，但顶部菜单未支持三级菜单。

表现为：

- 切换到顶部菜单后，`收单风控` 相关的三级菜单全部看不见；
- 用户无法打开三级菜单对应页面；
- 例如：
  - 收单风控 → 黑名单管理 → 卡号黑名单；
  - 收单风控 → 黑名单管理 → 卡指纹黑名单；
  - 收单风控 → 白名单管理 → 卡号白名单；
  - 收单风控 → 内风控规则管理 → 交易频率限定；
  - 其他三级风控菜单。

### 6.2 修复目标

顶部菜单必须支持至少三级菜单，建议支持递归多级菜单。

要求：

- 一级菜单显示在顶部导航栏；
- 二级菜单以下通过下拉、级联、子菜单或弹出层展示；
- 第三级菜单必须可见、可点击、可跳转；
- 三级菜单打开后，顶部一级菜单应保持正确高亮；
- 页签、面包屑、当前路由状态必须正确；
- 菜单权限必须与侧边菜单一致；
- 隐藏菜单、外链菜单、按钮权限不得错误展示。

### 6.3 实现要求

请检查当前顶部菜单是否存在以下问题：

- 只渲染了一层菜单；
- 只渲染到二级菜单；
- 使用 `children[0]` 作为默认跳转，导致更深层级被跳过；
- 顶部菜单和侧边菜单分别写了两套渲染逻辑；
- 顶部菜单没有递归组件；
- 有子菜单的节点点击逻辑和叶子节点点击逻辑混淆；
- `hidden`、`visible`、`permission`、`redirect`、`path` 的判断和侧边菜单不一致。

应改造为递归渲染：

```text
MenuTree
├─ MenuItem
├─ SubMenu
│  ├─ MenuItem
│  └─ SubMenu
│     ├─ MenuItem
│     └─ MenuItem
```

具体组件形式以当前 UI 组件库为准。

### 6.4 菜单点击规则

菜单节点分为两类：

#### 6.4.1 有子级菜单的节点

- 不应直接跳转到不存在的页面；
- 默认作为展开节点；
- 如果系统已有 redirect 配置，可按 redirect 跳转到第一个可访问叶子菜单；
- 如果没有 redirect，仅展开下级菜单。

#### 6.4.2 叶子菜单节点

- 点击后跳转到对应路由；
- 打开或激活对应页签；
- 更新面包屑；
- 更新顶部菜单高亮。

### 6.5 顶部菜单展示建议

当顶部一级菜单较多时：

- 保持现有顶部菜单样式；
- 不要因为本次修复破坏顶部右侧语言、设置、全屏、用户信息区域；
- 如顶部宽度不足，优先保持当前系统已有的溢出处理；
- 若当前没有溢出处理，不在本次大范围重构，但不能影响三级菜单展示。

### 6.6 顶部菜单验收标准

- [ ] 切换至顶部菜单后，`收单风控` 一级菜单可见；
- [ ] 鼠标悬停或点击 `收单风控` 后，二级菜单可见；
- [ ] `黑名单管理` 下的三级菜单全部可见；
- [ ] 点击 `卡号黑名单` 可以正常打开页面；
- [ ] 点击其他三级菜单可以正常打开页面；
- [ ] 打开三级菜单后顶部菜单高亮正确；
- [ ] 面包屑显示正确；
- [ ] 页签标题显示正确；
- [ ] 权限控制与侧边菜单一致；
- [ ] 切回侧边菜单后原有三级菜单仍正常；
- [ ] 不影响顶部右侧语言、设置、全屏、用户信息等功能。

## 7. 侧边菜单宽度拖拽规范

### 7.1 功能目标

侧边菜单栏和右侧主体内容之间增加可拖动的纵向分隔条。

用户可以拖动分隔条调整菜单宽度，从而查看较长菜单名称。

### 7.2 宽度规则

建议值：

```text
最小宽度：200px
默认宽度：当前系统现有宽度
最大宽度：420px
```

要求：

- 默认宽度保持现有系统视觉，不要上线后突然变宽；
- 必须设置最小宽度和最大宽度；
- 超出范围自动限制；
- 浏览器窗口变窄时不能导致主体区域完全不可用。

### 7.3 拖动交互

- 鼠标悬停菜单右侧边缘时显示：

```css
cursor: col-resize;
```

- 按住左键拖动时实时改变宽度；
- 拖动过程中禁止选中文本；
- 拖动过程中页面不得明显抖动；
- 松开鼠标后保存宽度；
- 右侧内容区域必须同步自适应。

### 7.4 折叠兼容

如果系统已有菜单折叠功能，必须保持兼容：

1. 折叠状态使用当前固定折叠宽度；
2. 折叠状态不允许拖动；
3. 展开后恢复用户上一次设置的宽度；
4. 用户未设置时使用系统默认宽度；
5. 不得破坏原有折叠按钮、菜单展开、路由跳转逻辑。

### 7.5 长菜单名称展示

菜单名称默认单行显示。

要求：

- 超出宽度使用省略号；
- 鼠标悬停展示完整名称 Tooltip；
- 不允许菜单名称覆盖图标或展开箭头；
- 不建议使用自动换行，避免菜单项高度不一致；
- 菜单图标位置保持稳定。

建议样式：

```css
overflow: hidden;
text-overflow: ellipsis;
white-space: nowrap;
```

### 7.6 菜单纵向滚动

当菜单内容超过窗口高度时：

- 菜单区域必须支持纵向滚动；
- 最底部菜单必须可访问；
- 不建议左侧菜单出现横向滚动条；
- Logo 区、折叠按钮、底部固定区域应根据当前布局合理处理。

### 7.7 菜单宽度保存

优先使用后端用户偏好接口。

如果暂无后端接口，则使用 `localStorage`。

建议缓存键：

```text
vexra:{appCode}:layout:sidebar-width:{userId}
```

示例：

```text
vexra:admin:layout:sidebar-width:10001
```

缓存读取要求：

- 非数字值忽略；
- 小于最小宽度时恢复默认值或最小值；
- 大于最大宽度时恢复默认值或最大值；
- 解析异常时不得影响页面加载；
- 不同用户互相隔离。

## 8. 页面主体布局规范

### 8.1 布局结构

建议统一布局：

```text
AppLayout
├─ Header / TopMenu
├─ Body
│  ├─ Sidebar
│  ├─ SidebarResizeHandle
│  └─ MainContent
```

实际命名以项目现有结构为准。

### 8.2 禁止固定偏移硬编码

禁止使用容易造成遮挡的固定写法，例如：

```css
margin-left: 240px;
```

应由统一布局容器根据菜单宽度动态分配。

### 8.3 滚动边界

必须区分：

- 菜单纵向滚动；
- 页面主体纵向滚动；
- 表格内部横向滚动。

表格字段过多时，不应推动整个浏览器产生横向滚动。

## 9. 标准列表页统一结构

标准列表页建议统一为：

```text
页面标题 / 页签
筛选区域
操作工具栏
表格工具栏
数据表格
分页区域
```

表格工具栏右侧建议统一放置：

- 刷新；
- 密度；
- 全屏；
- 编辑列。

如当前系统暂未实现刷新、密度、全屏，本次不强制新增，但“编辑列”必须作为标准列表能力接入。

## 10. 表格横向滚动规范

### 10.1 功能目标

当所有可见列总宽度超过表格容器宽度时，表格内部必须出现横向滚动条。

要求：

- 表格内部独立横向滚动；
- 表头和表体同步滚动；
- 分页区域不随表格横向滚动；
- 固定列保持正常；
- 当可见列总宽度小于表格容器宽度时，普通业务列必须按可用空间平铺展示，避免列内容集中在左侧并留下大面积空白；
- 不得让整个浏览器页面出现无意义横向滚动。

### 10.2 禁止无限压缩

不得为了让所有字段塞入一屏而无限压缩列宽。

每列必须具备：

- 默认宽度；
- 最小宽度；
- 必要时最大宽度。

### 10.3 固定列建议

- 多选框固定左侧；
- 序号列可固定左侧；
- 关键业务标识可根据业务需要固定；
- 操作列固定右侧。

固定列数量不宜过多，避免可滚动区域被压缩。

## 11. 表格列宽拖拽规范

### 11.1 功能目标

用户可以拖动表头列之间的边界，自由调整每一列宽度。

### 11.2 交互要求

- 鼠标移动到表头列右侧边界时显示 `col-resize`；
- 拖动时只调整当前列宽度；
- 不得触发表头排序；
- 不得选中页面文本；
- 表头宽度和表体宽度必须始终一致；
- 拖动结束后保存列宽；
- 刷新页面后恢复列宽。

### 11.3 可限制调整的列

以下列可以不支持或限制调整：

- 多选框；
- 展开按钮；
- 行序号；
- 极窄图标列；
- 特殊状态控制列。

业务数据列原则上都应支持调整宽度。

### 11.4 推荐列宽

| 字段类型 | 默认宽度建议 | 最小宽度建议 |
|---|---:|---:|
| 多选框 | 48px | 48px |
| 序号 | 64px | 60px |
| 状态 | 100px | 90px |
| 开关 | 90px | 80px |
| 普通短文本 | 140px | 120px |
| 商户号 | 150px | 130px |

| 流水号 | 240px | 200px |

### 11.5 超长内容

- 单行省略；
- 悬停 Tooltip 显示完整内容。

## 12. 编辑列统一规范

### 12.1 功能目标

每个标准列表表格右上角必须增加“编辑列”按钮。

按钮示例：

```text
⚙ 编辑列
```

图标优先使用当前 UI 组件库中的设置图标。

### 12.2 适用范围

适用于所有标准数据列表页面。

可不适用的页面：

- 两三列的小型嵌入式表格；
- 弹窗内临时明细表；
- 特殊矩阵表；
- 图表型页面；
- 非标准列表。

如果不适用，必须在页面配置中显式声明：

```text
columnSettingsEnabled = false
```

并注明原因。

### 12.3 面板结构

点击“编辑列”后打开 Popover、Dropdown 或 Drawer。

优先保持当前系统风格。

建议结构：

```text
固定列
  □ 多选框    禁用
  □ 操作      禁用

可编辑列                         重置
  ☑ 商户号                  拖动图标
  ☑ 商户名称                拖动图标
  ☑ 卡号                    拖动图标
  □ 来源                    拖动图标
```

### 12.4 固定列

以下列通常不可隐藏：

- 多选框；
- 序号；
- 核心业务标识；
- 操作列。

固定列在编辑列面板中可以展示，但应禁用选择，或单独展示在“固定列”区域。

### 12.5 列显示隐藏

要求：

- 通过复选框控制显示隐藏；
- 默认显示页面定义的默认字段；
- 取消勾选后立即隐藏；
- 重新勾选后立即恢复；
- 至少保留一个业务字段；
- 无权限字段不得出现在编辑列面板中。

### 12.6 列顺序调整

普通业务列支持调整顺序。

规则：

- 左侧固定列始终在最前；
- 右侧操作列始终在最后；
- 固定列不得拖入普通列区域；
- 普通列只能在普通列范围内排序；
- 调整后表格立即更新。

优先使用项目现有拖拽能力或组件库能力，不要随意引入大型依赖。

如果项目没有合适拖拽库，可先实现上移/下移按钮，保证稳定性优先。

### 12.7 重置

编辑列面板必须提供“重置”。

重置范围：

- 显示字段；
- 字段顺序；
- 字段宽度。

重置仅影响当前表格。

建议确认文案：

```text
确认恢复当前表格的默认列配置吗？
```

## 13. 表格配置模型规范

### 13.1 表格唯一标识 tableKey

每个标准表格必须设置稳定、唯一的 `tableKey`。

命名规则：

```text
{业务域}-{页面功能}-{表格用途}
```

示例：

```text
risk-card-blacklist-main
risk-card-fingerprint-blacklist-main
risk-bin-range-blacklist-main
risk-name-blacklist-main
risk-ip-blacklist-main
merchant-info-main
channel-mid-main
exchange-rate-source-main
mail-template-main
system-oper-log-main
```

禁止使用：

- 中文页面名称；
- 路由标题；
- 随机字符串；
- 列数组下标；
- 会频繁变化的组件名称。

### 13.2 列唯一标识 columnKey

每列必须有稳定的 `columnKey`。

推荐使用业务字段名：

```text
merchantNo
merchantName
cardNo
riskLevel
createdTime
```

禁止使用列下标作为唯一标识。

### 13.3 标准列定义建议

具体写法应结合当前技术栈，不要求机械照搬，但必须覆盖同等能力。

```ts
interface StandardTableColumn {
  key: string;
  title: string;
  dataIndex?: string;
  defaultVisible?: boolean;
  hideable?: boolean;
  resizable?: boolean;
  sortable?: boolean;
  fixed?: 'left' | 'right';
  defaultWidth?: number;
  minWidth?: number;
  maxWidth?: number;
  order?: number;
  permission?: string;
  tooltip?: boolean;
}
```

## 14. 用户偏好数据规范

### 14.1 统一存储

列宽、显示状态和顺序应统一存储，不建议拆成多个互相独立的缓存。

建议结构：

```json
{
  "version": 1,
  "tableKey": "risk-card-blacklist-main",
  "columns": [
    {
      "key": "merchantNo",
      "visible": true,
      "width": 160,
      "order": 1
    },
    {
      "key": "merchantName",
      "visible": true,
      "width": 220,
      "order": 2
    },
    {
      "key": "source",
      "visible": false,
      "width": 120,
      "order": 3
    }
  ],
  "updatedAt": 1783612800000
}
```

### 14.2 缓存键

建议：

```text
vexra:{appCode}:table-preference:{userId}:{tableKey}
```

示例：

```text
vexra:admin:table-preference:10001:risk-card-blacklist-main
```

### 14.3 配置合并规则

页面加载时，将代码默认列定义与用户历史配置合并。

规则：

1. 代码新增字段：
   - 自动加入；
   - 使用字段默认配置。

2. 代码删除字段：
   - 忽略历史配置中的旧字段。

3. 字段改名：
   - 视为旧字段删除、新字段新增；
   - 如需保留用户配置，应提供迁移映射。

4. 用户配置异常：
   - 忽略异常字段；
   - 使用默认配置；
   - 不得导致页面白屏。

5. 宽度超出范围：
   - 自动限制在 `minWidth` 和 `maxWidth` 之间。

6. 所有业务列被隐藏：
   - 自动恢复至少一个默认业务列。

### 14.4 配置版本

偏好数据必须包含版本号：

```json
"version": 1
```

后续模型升级时，通过版本做兼容或重置。

## 15. 安全与权限规范

### 15.1 编辑列不是权限控制

编辑列只控制用户界面展示，不代表用户有字段访问权限。

必须保证：

- 字段权限在列定义生成前就完成过滤；
- 用户无权限字段不出现在表格中；
- 用户无权限字段不出现在编辑列面板中；
- 后端不得因为前端隐藏字段而放松数据权限；
- 不得通过本地缓存恢复出用户无权限字段。

### 15.2 敏感字段保护

以下字段不得因编辑列功能被展示完整明文：

- 完整卡号；
- CVV；
- 密钥；
- 证书内容；
- 私钥；
- 公钥原文，如业务不允许；
- 访问令牌；
- 身份证件号；
- 其他敏感信息。

如必须展示，应使用脱敏值，例如：

```text
655545******5555
```

### 15.3 本地缓存安全

localStorage 只允许保存 UI 偏好，不得保存业务数据、敏感字段值或接口响应。

缓存内容必须可被安全忽略，不能影响权限判断。

- [ ] 固定列不能隐藏；

## 27. 一句话总约束

所有管理端标准列表页面必须使用项目统一表格能力，默认支持表格内部横向滚动、业务列宽度拖拽、编辑列、列显示隐藏、列顺序调整、列配置重置及用户偏好持久化。所有菜单模式必须基于同一份菜单树数据递归渲染，侧边菜单必须支持宽度拖拽、长名称省略和 Tooltip，顶部菜单必须支持三级及以上菜单。禁止业务页面重复实现上述能力，禁止使用页面级硬编码替代公共组件。
