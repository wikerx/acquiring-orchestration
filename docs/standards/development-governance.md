# 开发治理与规则执行规范

## 1. 目的

本规范定义 Vexra 收单系统开发规则如何组织、判定冲突、执行、验证和例外管理。它不重复 Java、Vue、OpenAPI、支付状态机等具体规则，而是规定这些规则如何生效。

## 2. 四层治理

| 层级 | 作用 | 适合内容 |
| --- | --- | --- |
| `AGENTS.md` | 进入目录后始终生效 | P0 不变量、权威顺序、修改边界、最低验证 |
| 目录级 `AGENTS.md` | 仅在所属模块生效 | OpenAPI、支付、清分、结算、前端应用专项约束 |
| Skill | 相关任务触发 | 分析、实施、审查、测试工作流和条件检查表 |
| 构建/测试/CI | 机械执行 | 编译、类型检查、单测、静态检查和契约测试 |

格式、编译、类型和可自动判断的规则，应尽量交给工具；业务语义、资金安全和兼容性仍需要设计与评审。

## 3. 权威来源

发生冲突时依次判断：

1. 已确认需求，以及经过批准且有版本的接口契约或 ADR；
2. 可执行契约，包括数据库结构、API 模型、测试、配置结构和已发布 SDK 行为；
3. 距离被修改文件最近的 `AGENTS.md`；
4. 持续维护的标准、API 和架构文档；
5. 通用手册、历史整改方案、样例和通用最佳实践。

同一层级冲突时，不采用“哪条更严格就选哪条”的简单规则。必须确认所属范围、发布日期、兼容承诺和实际所有者。若结论会改变公开接口、资金、状态、安全边界或数据库含义，应暂停并请求决策。

当前代码只能证明当前行为，不能单独证明目标行为；文档只能证明意图，不能单独证明已经实现。

## 4. 规则等级

| 等级 | 含义 | 处理方式 |
| --- | --- | --- |
| P0 | 阻断性不变量 | 不得静默绕过，违反时停止实施 |
| P1 | 新增和触达代码必须遵守 | 历史问题记录为技术债，不扩大本次范围 |
| P2 | 推荐改进 | 不影响当前目标和范围时实施 |

历史代码不符合 P1 时采用“触达治理”：只整改当前变更必要的部分，并通过测试证明兼容。禁止借规范治理进行无关的全仓格式化、重命名或搬包。

## 5. 变更风险

| 等级 | 范围 | 最低要求 |
| --- | --- | --- |
| R0 | 纯文档、注释且不改变行为 | 链接、路径和差异检查 |
| R1 | 模块内实现，不影响契约和持久化 | 定向测试和编译 |
| R2 | 跨模块、API、SQL、配置、缓存、消息、权限 | 所有者及依赖方验证、兼容场景 |
| R3 | 金额、结算、状态机、幂等、密码学、公开 OpenAPI、回调、对账、生产迁移 | 自动化回归、异常/重复场景、回滚或止损方案 |

## 6. DoR

开始修改前至少明确：

- 业务目标和不做什么；
- 所有模块、调用方、消费者和持久化事实；
- 使用的权威来源及尚未解决的冲突；
- P0/P1/P2 与 R0-R3；
- 兼容、灰度、回滚或止损要求；
- 验证命令、依赖环境和测试数据边界；
- 获得明确执行确认。

R3 变更中，任何会改变结果的关键问题未明确时，不得凭经验猜测。

## 7. DoD

变更完成必须满足：

- 已确认行为和非目标均被遵守；
- P0 不变量、外部兼容和数据语义未被破坏；
- 行为变化有测试，关键异常和重复场景有证据；
- 代码、契约、配置、SQL 和文档在需要时同步更新；
- 使用本轮新鲜命令输出报告验证结果；
- 未执行和失败的检查被如实说明；
- 技术债和例外有负责人及后续处理条件。

## 8. 例外与技术债

例外记录必须包含：规则、原因、影响、负责人、补偿措施、适用范围、到期或复审条件。永久性的“临时例外”无效。

发现范围外历史问题时，记录证据和风险，不在当前任务中顺手重构。只有 P0 风险直接阻止当前交付时，才暂停并升级处理。

## 9. 强制配置与启动门禁

新增或收紧“缺少配置即拒绝启动”的门禁时，必须在同一批变更中交付：

- dev、test、UAT、prod 的行为矩阵，明确哪些环境可使用隔离临时值、哪些必须由 Secret 系统注入；
- 不向 Git、日志或 Nacos 泄露密钥的本地引导或配置供应路径；
- 已有密文、数据和配置的兼容读取、迁移窗口及退出条件；
- 配置错误时可执行的错误提示，包含准确属性名和本地修复入口，不回显敏感值；
- 回滚或止损方案，以及所有读取该配置的服务启动契约测试。

不得把“删除弱默认值”当作完整整改。生产必须失败关闭，但开发环境也必须有稳定、可重复且不会破坏持久化数据的启动方案。

## 10. 规则维护

- 一条规则只保留一个权威位置，其他文件通过链接引用。
- 根约束只保留跨任务不变量；模块细节下沉到目录级文件。
- Skill 只描述工作流和条件检查，不复制整本手册。
- 历史整改计划保留为背景，不继续作为永久执行指令。
- 规则修改必须说明原因、影响范围和如何验证，避免在多个仓库产生语义不同的副本。
