# 代码评审规范

## PR 描述要求

PR 描述必须说明：

1. 背景与目标。
2. 核心改动点。
3. 风险与回滚方案。
4. 测试结果。
5. 是否涉及资金、安全、合规、数据库变更。

## Reviewer 检查清单

- 业务逻辑是否符合需求和状态机设计。
- 是否存在重复支付、重复入账、重复通知风险。
- 幂等键、事务边界、分布式锁和重试策略是否清晰。
- 金额、币种、汇率、手续费计算是否精确且可审计。
- 外部渠道异常是否被正确分类和降级。
- 敏感信息是否脱敏，密钥是否未进入代码仓库。
- 日志、监控、告警是否足够定位生产问题。
- 数据库变更是否兼容老数据和灰度发布。
- 是否有必要的单元测试、集成测试和回归测试。

## 评论分级

- `blocker`：必须修改，否则存在生产事故、资金损失、安全或合规风险。
- `major`：应修改，可能导致缺陷、可维护性明显下降或测试不足。
- `minor`：建议修改，命名、可读性、边界处理等问题。
- `nit`：非阻塞建议。

## 合并规则

1. 所有 `blocker` 和 `major` 评论必须关闭后才能合并。
2. 作者不得自行合并未通过审核的 PR。
3. Reviewer 对支付资金链路有疑问时，默认阻塞合并，直到设计或测试证据充分。
4. 大型 PR 应拆分为可独立评审的小 PR。
