# 代码评审规范

## PR 描述要求

PR 描述必须说明：

1. 背景与目标。
2. 核心改动点。
3. 风险与回滚方案。
4. 测试结果。
5. 是否涉及资金、安全、合规、数据库变更。

## Reviewer 检查清单

- 业务逻辑是否符合需求和状态机设计。
- 是否存在重复支付、重复入账、重复通知风险。
- 幂等键、事务边界、分布式锁和重试策略是否清晰。
- 金额、币种、汇率、手续费计算是否精确且可审计。
- 外部渠道异常是否被正确分类和降级。
- 敏感信息是否脱敏，密钥是否未进入代码仓库。
- 日志、监控、告警是否足够定位生产问题；日志是否使用中文事件描述、稳定英文事件码/字段名和 `field: {}` 参数格式，并遵守级别与脱敏边界。
- 数据库变更是否兼容老数据和灰度发布。
- 是否有必要的单元测试、集成测试和回归测试。

## 评论分级

- `P0 / blocker`：必须修改；存在资金、安全、合规、状态一致、数据损坏或公开契约破坏风险。
- `P1 / major`：合并前应修改；存在明确缺陷、遗漏的异常路径、兼容风险或必要测试缺失。
- `P2 / minor`：建议在当前范围内修改；不影响正确性，但会造成可维护性或一致性问题。
- `nit`：非阻塞偏好；不得用个人风格要求覆盖项目既有约定。

评审意见必须包含证据、影响和可执行建议。不能仅以“更严格”作为理由；发生规则冲突时，按根 `AGENTS.md` 的权威顺序确定适用规则。

## 合并规则

1. 所有 `P0/blocker` 和 `P1/major` 评论必须关闭或经过有记录的例外审批后才能合并。
2. 作者不得自行合并未通过审核的 PR。
3. Reviewer 对支付资金链路有疑问时，默认阻塞合并，直到设计或测试证据充分。
4. 大型 PR 应拆分为可独立评审的小 PR。
