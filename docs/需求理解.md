## 需求概述

为系统中长期处于“处理中的”收单交易增加自动渠道查询勾兑能力。系统定时按批次扫描超过等待阈值的非终态交易，使用原交易实际落库的渠道和渠道 MID 发起查询，并根据渠道明确返回的成功、失败或处理中状态推进系统交易。渠道明确返回“订单不存在”时，认定原渠道创建失败并将系统交易置为失败；网络异常、超时、响应无法解析或渠道仍处理中不能直接判定为失败。

勾兑、退款、撤销等后续渠道动作必须使用原交易冻结的渠道身份和原始交易 MID。商户当前绑定的新渠道或新 MID 只能用于新交易，不能影响历史交易的查询和后续动作。

## 功能需求

### P0 - 必须实现

- [ ] 自动扫描：新增或配置定时任务，扫描等待超过 5 分钟且仍处于非终态的交易。
- [ ] 分批处理：每次最多处理 100 条，按交易时间和下一次勾兑时间从旧到新处理；本次未处理完的历史数据由后续调度继续处理。
- [ ] 原渠道路由：勾兑必须使用交易操作单保存的 `channelCode`、`channelId`、`channelMidConfigId`、渠道订单号和渠道交易号，禁止重新执行商户路由。
- [ ] 原始 MID：原交易使用的 MID、请求地址、版本和渠道元数据必须在交易创建时冻结；原 MID 被停用、商户改绑新 MID 或当前路由配置变化时，历史勾兑仍访问原 MID。
- [ ] 状态同步：渠道明确返回成功时推进系统成功，明确返回失败时推进系统失败，渠道仍处理中时保持系统非终态并安排下一次查询。
- [ ] 渠道订单不存在：只有渠道明确返回“订单不存在/查无此单”时，才将系统交易置为失败，并记录“渠道交易创建失败”的失败原因。
- [ ] 不确定结果保护：网络超时、连接失败、HTTP 5xx、渠道响应无法解析、状态无法映射、缺少查询身份等情况不得直接将交易标记为失败。
- [ ] 幂等与并发：同一交易被定时任务、人工重查或渠道回调同时处理时，使用版本 CAS 和终态保护，不能重复推进状态、金额或商户通知。

### P1 - 重要功能

- [ ] 任务支持渠道筛选、分片时间定位和运行结果统计，能够查看扫描数、成功数、失败数、继续等待数和异常数。
- [ ] 任务支持历史已发布交易分片的完整回看，不因默认只回看最近季度而遗漏长期处理中订单。
- [ ] 对查询失败、状态冲突、金额/币种不一致、原 MID 不可用等情况保留可追踪的勾兑结果、失败原因和下一次查询时间。
- [ ] 任务具备分布式互斥或等价的领取机制，多个 Job 实例不能重复领取同一批订单。
- [ ] 交易因渠道明确失败或明确查无此单进入终态时，按现有交易结果通知协议触发商户通知；通知失败由现有通知重试链路处理。

### P2 - 可选功能

- [ ] 管理端支持对单笔交易使用原 MID 手动重新勾兑。
- [ ] 管理端展示原交易渠道、原 MID、渠道订单号、最近查询时间、查询次数和下一次查询时间。

## 非功能需求

- 性能：单次默认 100 条；单笔渠道查询超时和任务总运行时间必须有上限，避免长时间占用调度线程。
- 一致性：只有渠道统一响应被可靠解析且通过状态/金额/币种校验时才推进交易；终态交易不被自动覆盖，状态冲突进入勾兑异常处理。
- 安全：原 MID 的 API Key、Callback Secret 等敏感元数据不得写入 Redis、普通日志或管理端明文；勾兑调用必须复用原交易的敏感配置快照或受控密文读取。
- 可用性：单笔查询失败不能阻断同批其他交易；任务失败后下一次调度能够继续领取未完成订单。
- 可追踪：每次查询记录请求引用、原渠道/MID、渠道响应状态、系统映射状态、结果摘要、失败原因和下一次查询时间。

## 边界与约束

- 不允许按照当前商户路由重新选择渠道或 MID。
- 不允许因为网络错误、渠道暂时不可用或渠道仍处理中而直接标记交易失败。
- 不允许自动把已成功或已失败的系统终态改成相反状态；终态与渠道不一致时只更新勾兑状态并进入异常处理。
- 不在本需求中新增人工终态修正、资金补偿或绕过交易状态机的 SQL 更新。
- 查询接口必须由对应渠道适配器明确支持；不支持查询的渠道需要进入可监控的异常/人工处理路径，不能假装查询成功。

## 验收标准

### 自动扫描和批量处理

- Given 存在超过 5 分钟且仍为非终态、`channel_match_status=PENDING` 的交易，When 定时任务触发，Then 最多领取 100 条并按原交易渠道/MID逐笔查询，任务返回各类处理数量。
- Given 历史记录超过 100 条，When 一次任务结束，Then 未处理记录不会丢失，后续任务可以继续从最早的待处理记录开始，直到队列为空。
- Given 两个 Job 实例同时扫描，When 处理同一批记录，Then 同一交易最多只有一个版本更新成功，不能重复调用造成重复状态推进。

### 原渠道和原始 MID

- Given 交易创建后商户改绑了新的 MID，When 对历史交易执行勾兑或退款，Then 请求仍使用原交易冻结的渠道编码、原 `channelMidConfigId`、原渠道订单号和原渠道交易号。
- Given 原 MID 被停用但仍有未终态交易，When 执行历史勾兑，Then 系统仍能读取原 MID 的受控查询配置；禁止静默切换到新 MID。
- Given 原 MID 配置已经被删除或缺少可用的历史凭据，When 执行勾兑，Then 交易不自动改为失败，记录“原始 MID 配置不可用”并进入人工处理/告警路径。

### 渠道结果映射

- Given 渠道查询明确返回成功，When 交易仍为非终态，Then 按现有交易状态机推进为成功，写状态历史、必要的金额事件和商户通知 Outbox。
- Given 渠道查询明确返回失败，When 交易仍为非终态，Then 按现有交易状态机推进为失败，并保存渠道失败码和失败原因。
- Given 渠道查询明确返回处理中或待回调，When 任务处理，Then 系统保持非终态，增加查询次数并安排下一次查询。
- Given 渠道明确返回订单不存在，When 任务处理，Then 系统置为失败，失败原因明确显示为“渠道交易创建失败/渠道订单不存在”。
- Given 查询超时、网络异常、5xx 或响应无法解析，When 任务处理，Then 系统不置失败，只记录查询异常并安排后续重试。
- Given 系统交易已经是成功或失败终态，When 渠道查询返回相反状态，Then 不自动覆盖交易终态，只更新勾兑状态并生成可追踪异常。

## 待确认决策

1. “处理中的订单”是否只包含 `transaction_status=PROCESSING`，还是包含 `PENDING` 等所有非终态？建议默认包含 `PENDING` 和 `PROCESSING`，但排除尚未提交且仍在 INIT/SENT 保护窗口内的请求。
2. 5 分钟从哪个时间点计算？建议以最后一次真实渠道请求的 `request_start_time`（没有时回退到交易创建时间）计算，而不是以上一次定时任务时间计算。
3. 每次 100 条是全系统总量、每个渠道 100 条，还是每个交易分片 100 条？建议定义为一次任务全局最多 100 条，避免多个分片叠加造成实际超量。
4. “直到历史交易全部处理完成”是指一次任务在同一执行中循环清空，还是每次执行 100 条、由下一次调度继续？建议采用后者，并设置单次运行时间上限。
5. 定时任务频率、最大并发实例数和单笔查询超时时间是多少？建议先按每 1 分钟触发、单实例执行、单笔超时沿用渠道配置，并通过分布式锁防重入。
6. 渠道返回“订单不存在”需要渠道适配器提供统一的明确结果码；请确认各渠道的查无此单状态/HTTP 码是否能逐一映射，不能把普通 404、网关错误或超时一律视为订单不存在。
7. 原 MID 被停用或密钥轮换后，是否允许继续使用历史冻结的敏感配置直到所有关联订单结束？建议允许历史勾兑继续使用受控密文快照，并禁止删除仍有未终态交易引用的原 MID。
8. 渠道仍处理中超过多长时间后进入人工复核或告警？建议保留自动重试，但按渠道 SLA 配置升级阈值，不能无限无告警地轮询。
9. 渠道失败/查无此单后是否立即向商户发送失败回调？建议复用现有终态通知协议，并确认“渠道交易创建失败”的商户可见文案和错误码。
